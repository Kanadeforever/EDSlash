# BladeSwordQOL 架构与模块开发规范

## 1. 目标

项目最终形态是“一个 Universal ASI + 多个内部模块 + 两个游戏 Profile”。模块是源码/功能边界，不是 DLL 边界。

```text
BladeSwordQOL.asi
  ├─ Runtime
  ├─ DaoJian Profile
  ├─ WaiZhuan Profile
  ├─ DisplayFix Module
  ├─ Controller Module（下一阶段）
  ├─ QoL Modules（后续）
  └─ Gameplay Modules（后续）
```

## 2. 绝对规则

0. 包根必须严格只有 `docs / source / release`；统一源码工程固定放在 `source/BladeSwordQOL/`。

1. `DllMain / InitializeASI` 只能存在于 `source/BladeSwordQOL/src/Main.c`。
2. 游戏识别只能由 Runtime 做一次。
3. Module 不得自己再次判断“本体还是外传”。
4. Module 不得绕过 GameProfile 直接复制另一套地址表。
5. 公共物理 Hook 只能有一个提供者。
6. 其它模块需要同一个生命周期时必须订阅 EventBus。
7. 不因为“架构漂亮”而一次性重写已经实机稳定的旧 Hook；按实际共享需求逐条上提。
8. 模块之间尽量不直接调用彼此，优先通过 Runtime service/event 交互。

## 3. GameProfile

当前 v0.1-dev1 用 PE32 `SizeOfImage + EntryPoint RVA` 做第一层识别，然后由 DisplayFix 后端自己的机器码签名继续做第二层验证。

本体：

```text
SizeOfImage = 0x00173000
EntryPoint  = 0x0010F0EF
```

外传：

```text
SizeOfImage = 0x001A5000
EntryPoint  = 0x00127BCF
```

未知 EXE 必须 fail-open：不打补丁。

## 4. ModuleRegistry

模块统一实现初始化入口并在 `ModuleRegistry.c` 注册。Runtime 不直接写死具体模块业务。

Registry 必须具备**模块级故障隔离**：某一个模块初始化失败，只标记该模块失败并继续后面的模块；不能因为某个前序可选模块初始化失败就阻止未来 Controller/QoL 启动。当前通过 `ModuleRegistry_IsInitialized()` 保存/查询每个模块的初始化状态。

当前：

```text
DisplayFix
```

计划：

```text
DisplayFix
Controller
QoL
Inventory
GroundItem
AutoPickup
Gameplay
```

禁用某模块最终应由统一 INI 决定，而不是删 DLL。

## 5. HookManager

HookManager 解决的是“物理 Hook 所有权”。例如 Strategy、UI Draw、Input Frame 之类入口只能有一个代码提供者。

模块在真正安装物理 Hook 以前可能需要连续 Claim 多个共享入口；任何一个 Claim 失败都必须回滚本模块已经取得的 owner 槽。当前 `HookManager_ReleaseOwned()` 专门用于这种**初始化阶段的声明回滚**，它不是热卸载器，也不会修改已经写进游戏内存的机器码。

当前已登记：

- Strategy lifecycle
- Main HUD layout
- UI manager Draw
- UI root picker
- World mouse press
- Global mouse release

v0.1-dev1 为了保持 DisplayFix 等价，具体 patch 仍由两个 DisplayFix Profile 后端安装；HookManager 先负责防止未来模块重复声明。后续当 Controller 第一次需要共享某个入口时，再把这个入口的安装器抽到 Runtime。

## 6. EventBus

当前语义事件：

```text
GAMEPLAY_ENTER
GAMEPLAY_EXIT
UI_DRAW_BEGIN
UI_DRAW_END
```

DisplayFix 已在两个 Profile 后端广播这些事件。Controller 不应 Hook Strategy/UI Draw，而应该订阅。

未来可能新增：

```text
INPUT_FRAME_PRE
INPUT_FRAME_REMAP
INPUT_FRAME_POST
UI_ROOT_SELECTED
GROUND_ITEM_UPDATE
GROUND_ITEM_PICKUP_REQUEST
```

事件阶段必须有明确顺序，禁止多个模块通过“谁最后写内存谁赢”来决定行为。

## 7. Controller 下一阶段原则

手柄支持直接作为 `source/BladeSwordQOL/src/Modules/Controller/` 加入本工程。

优先工作顺序：

1. 先找游戏统一输入帧入口；
2. Runtime 只 Hook 一次；
3. 将原始键鼠/手柄状态包装成共享 Input Service；
4. Controller 模块做按键映射、鼠标模式、震动、UI 焦点；
5. QoL 若以后也需要输入，只订阅相同输入事件；
6. 不允许 Controller 再直接 Hook DisplayFix 已占用的 UI Draw/Strategy callsite。

## 8. Profile 差异边界

模块中禁止出现大量：

```c
if (game == DAOJIAN) address = ...;
else address = ...;
```

长期应由 Profile 提供语义服务/地址。v0.1-dev1 的 DisplayFix 后端仍是历史单文件迁移，因此内部保留各自地址与签名；这是兼容迁移阶段，不是未来新模块模板。

## 9. 失败开放

任何 Profile/signature/hook 条件验证失败：

- 不猜地址；
- 不部分写入；
- 不尝试另一游戏后端；
- 当前模块尽量保持游戏原版；
- 日志记录具体失败点。
