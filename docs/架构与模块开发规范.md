# BladeSwordQOL 架构与模块开发规范

> 当前状态（2026-10-01，以 source 为准）：主插件注册 DisplayFix＋QOL；Controller 独立构建为 v0.1-dev7。dev6 交接与本体防御扣费已有用户确认；闪避失败，dev7 新快捷／套组／体力规则待两作实机。旧节保留阶段证据，当前状态以本入口和最新章节为准。

> Controller 硬性要求（2026-09-27）：同一独立 ASI 同时支持非 Steam 本体 1.05 与外传 2.01，功能与验证必须两版成对完成；Steam 后置不代表外传后置。早期基础版的两作最终验收当时待完成；当前源码已到 dev7，已确认与待测范围以最新接档为准，完整操控仍有未实现项。

## 1. 目标

项目最终形态仍是“一个 Universal ASI + 多个内部模块 + 两个游戏 Profile”。2026-09-27 用户明确：Controller 当前先独立构建、独立测试，但始终是本项目子模块，源码位于 `source\src\Modules\Controller\`，不另建根目录工程。独立产出是当前开发阶段安排，不改变主项目目录结构。

```text
BladeSwordQOL.asi
  ├─ Runtime
  ├─ DaoJian Profile
  ├─ WaiZhuan Profile
  ├─ DisplayFix Module
  ├─ Controller Module（下一阶段）
  ├─ QOL Module（已注册：名称／分类／拾取）
  └─ Gameplay Modules（后续）
```

## 2. 绝对规则

1. 主插件 `BladeSwordQOL.asi` 的 `DllMain / InitializeASI` 只能存在于 `source\src\Main.c`。Controller 当前独立目标的入口位于其模块目录，不加入主插件构建；未来合并时必须移除独立入口。
2. 游戏识别只能由 Runtime 做一次。
3. Module 不得自己再次判断“本体还是外传”。
4. Module 不得绕过 GameProfile 直接复制另一套地址表。
5. 公共物理 Hook 只能有一个提供者。
6. 其它模块需要同一个生命周期时必须订阅 EventBus。
7. 不因为“架构漂亮”而一次性重写已经实机稳定的旧 Hook；按实际共享需求逐条上提。
8. 模块之间尽量不直接调用彼此，优先通过 Runtime service/event 交互。
9. 包根固定为 `docs\ / source\ / release\`；源码直接从 `source\src\` 开始，禁止额外增加工程名中间层。

## 3. GameProfile

当前 v0.1-dev1 用 PE32 `SizeOfImage + EntryPoint RVA` 做第一层识别，然后由 DisplayFix 后端自己的机器码签名继续做第二层验证。

本体：

```text
SizeOfImage = 0x00173000
EntryPoint  = 0x0010F0EF
```

外传：

```text
SizeOfImage = 0x001A5000
EntryPoint  = 0x00127BCF
```

未知 EXE 必须 fail-open：不打补丁。

## 4. ModuleRegistry

模块统一实现初始化入口并在 `ModuleRegistry.c` 注册。Runtime 不直接写死具体模块业务。

Registry 必须具备**模块级故障隔离**：某一个模块初始化失败，只标记该模块失败并继续后面的模块；不能因为某个前序可选模块初始化失败就阻止未来 Controller/QoL 启动。当前通过 `ModuleRegistry_IsInitialized()` 保存/查询每个模块的初始化状态。

当前：

```text
DisplayFix
QOL
```

Controller 当前独立构建。GroundItems、ItemClassifier、AutoPickup 是 QOL 内部职责，不是 Registry 的多个平级模块；未来扩展只在实际实施时登记。

主插件业务开关从同目录 INI 读取。Registry 状态只保存初始化返回值；DisplayFix 有效句柄下返回 1，不等于其内部所有 patch 均成功，须核对后端日志。

## 5. HookManager

HookManager 解决的是“物理 Hook 所有权”。例如 Strategy、UI Draw、Input Frame 之类入口只能有一个代码提供者。

模块在真正安装物理 Hook 以前可能需要连续 Claim 多个共享入口；任何一个 Claim 失败都必须回滚本模块已经取得的 owner 槽。当前 `HookManager_ReleaseOwned()` 专门用于这种**初始化阶段的声明回滚**，它不是热卸载器，也不会修改已经写进游戏内存的机器码。

当前已登记：

- Strategy lifecycle
- Main HUD layout
- UI manager Draw
- UI root picker
- World mouse press
- Global mouse release
- GroundItem Update
- Input Frame
- PickupEntry

v0.1-dev1 为了保持 DisplayFix 等价，具体 patch 仍由两个 DisplayFix Profile 后端安装；HookManager 先负责防止未来模块重复声明。后续当 Controller 第一次需要共享某个入口时，再把这个入口的安装器抽到 Runtime。

## 6. EventBus

当前语义事件：

```text
GAMEPLAY_ENTER
GAMEPLAY_EXIT
UI_DRAW_BEGIN
UI_DRAW_END
```

DisplayFix 已在两个 Profile 后端广播这些事件。同一 ASI 内的 Controller 应订阅这些事件。当前独立 ASI 阶段不能假定可跨 DLL 直接使用主插件内部 EventBus；必须另行核对共存入口，不能重复覆盖 DisplayFix 的 Strategy/UI Draw。

未来可能新增：

```text
INPUT_FRAME_PRE
INPUT_FRAME_REMAP
INPUT_FRAME_POST
UI_ROOT_SELECTED
GROUND_ITEM_UPDATE
GROUND_ITEM_PICKUP_REQUEST
```

事件阶段必须有明确顺序，禁止多个模块通过“谁最后写内存谁赢”来决定行为。

## 7. Controller 下一阶段原则

手柄支持直接作为 `source\src\Modules\Controller\` 加入本工程。

当前独立目标已形成 v0.1-dev2 调查与操作修正版，入口为 `source\build_controller.bat`，源码位于模块目录，工具位于 `source\tools\controller\`。两版静态与适配回放通过，尚待两作实机验收；完整功能缺项见《手柄模块接档说明.md》。SDL 与磁盘散列在首个游戏输入帧初始化，不在 DllMain 的 Loader 锁内执行。

以下为未来合入统一 Runtime 时的工作顺序：

1. 先找游戏统一输入帧入口；
2. Runtime 只 Hook 一次；
3. 将原始键鼠/手柄状态包装成共享 Input Service；
4. Controller 模块做按键映射、鼠标模式、震动、UI 焦点；
5. QoL 若以后也需要输入，只订阅相同输入事件；
6. 不允许 Controller 再直接 Hook DisplayFix 已占用的 UI Draw/Strategy callsite。

## 8. Profile 差异边界

模块中禁止出现大量：

```c
if (game == DAOJIAN) address = ...;
else address = ...;
```

长期应由 Profile 提供语义服务/地址。v0.1-dev1 的 DisplayFix 后端仍是历史单文件迁移，因此内部保留各自地址与签名；这是兼容迁移阶段，不是未来新模块模板。

## 9. 失败开放

任何 Profile/signature/hook 条件验证失败：

- 不猜地址；
- 不部分写入；
- 不尝试另一游戏后端；
- 当前模块尽量保持游戏原版；
- 日志记录具体失败点。

## 当前 QOL 与 Runtime 使用边界（source 核对）

QOLModule 读取配置、验证三入口、Claim 并安装。GroundItems 负责名称、落地与生命周期；ItemClassifier 读取 Type；AutoPickup 定位唯一原生动作并同步调用 action=22。详细机制见《自动拾取与地面物品名称说明.md》。Controller 将来合入必须共享现有 Input Frame 物理入口；独立 ASI 不能直接使用主插件内部 EventBus。

Win32Bridge 从已识别 Profile 的主 EXE IAT 基础槽解析 API。必需 API 缺失让桥不可用，日志 API 单独可选；主目标保持零导入。新增 API 应在桥初始化中解析和检查，不直接带入系统／CRT 导入。

X86Detour 覆盖长度为 5～16 字节，不反汇编、不修复复制指令的相对引用；调用者必须确认完整指令边界并先验证原字节。WriteCode 返回 0 为写前失败、1 为写入与附加处理完成、2 为已写但缓存／保护处理失败。Install 对 2 保留安装记录并返回成功，不能视为附加处理均成功。Remove 核对自身 patch 或已恢复原字节，完整恢复后才释放网关。

QOL 回滚先关闭自动业务，三个入口各自撤销；任一失败保留 owner。DisplayFix 仍使用各后端安装器，Controller 使用独立 patch／Guard；这些不是所有模块统一具备的热卸载能力。

UI_DRAW_BEGIN 在原版 UI manager Draw 前发出，UI_DRAW_END 在它返回后发出。通常延迟菜单在 HUD wrapper 内补画，但 END 后仍可能帧末补画剩余 GUI；END 不是全部 UI 呈现完成通知。GAMEPLAY_ENTER 只在配置与 live 尺寸匹配时发出；EXIT 在清理和尝试前端恢复后发出，恢复结果仍需日志确认。
