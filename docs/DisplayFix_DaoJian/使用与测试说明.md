# DisplayFix v0.3-test10 使用与测试说明

## 运行文件

正式发行目录只有：

- `DisplayFix.asi`
- `DisplayFix.ini`

放到游戏 ASI Loader 能加载的位置即可。运行后会在插件同目录生成 `DisplayFix.log`。

## 推荐配置

```ini
[Display]
Enable=1
BaseHeight=720
AspectRatio=Auto

[Font]
FixDPI=1

[GUI]
CenterMainHUD=1
```

`BaseHeight` 是逻辑纵向高度，也会改变世界可视范围；不是单纯的输出画质参数。

## v0.3-test10 当前重点测试

`BaseHeight`/INI 修复已经由 test8b 日志确认；顶部属性/道具输入链也继续沿用 test8 的已通过方案。test10 当前只验证 Steam/ComeOn.dll 缺失的“完整第二阶段 JMM 应用”。

### 为什么 test9 已经判定失败

test9 在 Steam 下实际记录到：

```text
visited=34
applied=34
done=1
id0B_before == id0B_after
id0E_before == id0E_after
```

也就是说 34 个顶层 UI 的 `vtable+0x14` 都执行了，但真实 HUD 子控件没有移动，GUI 仍然错误。因此 test10 不再使用“只广播尺寸”方案。

### Steam 版重点

建议继续使用：

```ini
BaseHeight=720
AspectRatio=Auto
CenterMainHUD=1
```

启动并进入游戏，不要先手工切换分辨率。正确初始化日志应包含：

```text
[INFO] Steam/ComeOn.dll environment detected
[OK] Steam delayed JMM apply armed; waits for mature HUD + top-level UI + resource root
[INFO] Steam fix reuses original 0x4B35F0 once; non-Steam path remains untouched
```

HUD、顶层 UI 和游戏资源根目录都成熟后，应只出现一次：

```text
[RUNTIME] Steam delayed JMM apply begin ... resource_root=ready ...
[RUNTIME] Steam delayed JMM apply end result=1 done=1 child_layout_changed=1 ...
```

最重要的验收点：

- GUI 是否进入和非 Steam 相同的最终布局；
- `id0B_after / id0E_after` 是否相对 before 发生第二阶段位置变化；
- 帧数/游戏速度是否维持 test9 已恢复到约 50+ 的状态；
- 不应出现 `MB\JMMDL.txt` 或 `MB\JMMDL800.txt` 弹窗。若出现，立即退出并提供完整日志，不要继续测试。

### 非 Steam 回归

非 Steam 日志应只有：

```text
[INFO] non-Steam environment detected; Steam delayed UI sync remains dormant
```

不得出现 `Steam delayed JMM apply begin/end`。非 Steam GUI 必须保持此前正常状态。

### 输入回归

两种环境都至少确认：普通地图左键可移动、属性/道具可开关且不移动角色、右侧鼠标技能设置按钮正常、Alt+F4 正常。test10 不修改 test8 的输入链。

如果出现问题，请提供完整 `DisplayFix.log`。

## BaseHeight

没有人为上限。示例 16:9：

- 480 -> 约 854x480
- 540 -> 960x540
- 600 -> 约 1067x600
- 720 -> 1280x720
- 1080 -> 1920x1080

极端值可能超过老 DirectDraw/游戏 Surface 能力，属于游戏本身限制。

## 已知未解决

- 主界面固定 640x480 目前还不会自动 4:3 等比放大并居中。
- Steam GUI 已进入 test10“延迟完整原版 JMM apply”验证阶段；速度/帧数仍需实机确认。
- 这两项与本轮 test8 的顶部按钮穿透修复分开处理。

## v0.3-test8a 同步说明

- `v0.3-test8` 实机确认已经修复 test7 的普通地图左键 / Alt+F4 回归，并保留属性、道具两个顶部按钮响应；当前输入实现继续沿用 test8。
- test8 日志显示用户把 `BaseHeight` 改为 1080 后插件仍读取成 480。复核发行 INI 后确认 `[Display]` 原本正好位于 UTF-8 BOM 后的第一行；Win32 `GetPrivateProfile*A` 对 UTF-8 BOM 不可靠，第一节可能读不到，于是 `BaseHeight` 静默使用默认 480。test8a 将 INI 改为 UTF-8 无 BOM，并在 `[Display]` 前增加 ASCII 保护行，使以后编辑器即使重新加入 BOM，也不会再破坏第一节。
- test8a 日志新增 `ConfigPath=`，用于直接确认插件实际读取的是哪一份 `DisplayFix.ini`。
- `build.bat` 已按仓库位置重新整理：同时自动查找 PATH、`LLVM_HOME`、`LLVM_PATH`、`Program Files\LLVM` 和 Visual Studio 自带 LLVM，兼容本地与 Windows GitHub Actions；发行目录仍严格只有 ASI 与 INI。
- 主界面固定 640x480 的等比放大居中仍是后续任务，本轮没有处理。



## v0.3-test8b 构建同步说明

- test8a 的 `build.bat` 最后使用 `where /r` 递归扫描 Visual Studio，实机误选到 `VC\Tools\Llvm\ARM64\bin\clang.exe`，在 x64 Windows 上出现“映像文件无效 / 对另一种计算机类型有效”。该方案已判定失败。
- test8b 将编译器搜索精简为三层：PATH → `%ProgramFiles%\LLVM\bin` → `vswhere` 最新 Visual Studio 的 `VC\Tools\Llvm\x64\bin`；`clang.exe` 与 `lld-link.exe` 必须来自同一目录。
- 不再支持递归扫描、`LLVM_HOME`、`LLVM_PATH` 或任意 ARM64 LLVM 回退。找到工具后先运行 `--version`，无法在当前宿主执行时立即停止。
- `verify_build.py` 新增 build.bat 自检：禁止 `where /r`、禁止 ARM64 LLVM 路径、要求存在 x64 VS LLVM 回退，并检查 UTF-8 BOM + CRLF 以及所有有正文的 `REM` / `echo` 行末尾两个半角空格。
- test8b 后续实机日志已经确认 INI 第一节修复成立：Steam 与非 Steam 都能正确读取 `BaseHeight=720` 并计算 `1280x720`；这一项不再是阻塞。
