# DisplayFix 使用与测试说明（截至 v0.3.4-stripe1，稳定基线另行保留）

## 2026-09-15 stripe1 当前同步（本节优先级最高）

- **当前竖条实验版：本体 `v0.3.4-stripe1` / 外传 `v0.2.3-stripe1`。** 本体 GUI/输入基线 `v0.3.3-layer1d` 已由用户实机确认最后生命周期边界也解决；外传仍不能用本体结果代替独立实机。
- 本轮只处理从早期宽屏阶段就存在的**最右侧竖条纹**，不扩大 GUI/Input Hook。用户在 `BaseHeight=480` 下实测：`16:9 / 32:9 / 8:9 / 40:9` 有竖条，`24:9` 没有。
- 旧宽度算法会得到：`16:9 -> 854 (mod8=6)`、`32:9 -> 1708 (mod8=4)`、`8:9 -> 428 (mod8=4)`、`40:9 -> 2134 (mod8=6)`、`24:9 -> 1280 (mod8=0)`。目前所有有问题样本的实际 `TargetWidth` 都**不是 8 像素倍数**，唯一无问题样本 `1280` 恰好是 8 像素倍数。
- 因此 stripe1 的单一实验变量是：把最终 `TargetWidth` 从“按比例四舍五入后只保证偶数”改成“**选择距离理想比例最近的 8 像素倍数**”。对应上述样本，新宽度为 `856 / 1704 / 424 / 2136 / 1280`。
- 这仍是**待实机验证的根因假设**，目前不能把“8 像素块处理”写成已确认事实。若 stripe1 消除竖条，才可把根因升级为已实机闭合；若竖条仍在，则立即回退，不继续扩大改动。
- `layer1d` 已通过的辅助 GUI HUD 后绘制、顶层 picker 单次返回值覆盖、独立面板短生命周期跟踪、Strategy FRONTEND/GAMEPLAY、Steam delayed JMM、96-DPI、0x0B/0x0E 防穿透全部保持不变。外传 Steam `ResJM.Lib`、ComeOn.dll class-atom 与官方 EDIT WndProc 红线也不变。
- 两套 `verify_build.py` 已新增 stripe1 防回归：要求 `TargetWidth` 使用 8 像素边界算法、旧“只补偶数”运行代码为 0，并继续锁住 layer1d GUI/Input 红线。
- 当前构建 SHA-256：本体 `f565b4d683746fcf9d1fa30d9728df66c7e4e83676758b69a40693ccbebb6b8e`；外传 `deb40b447c94dedd2301a665c59e27dfa3fdb3e2ff44dccc55a46e813b33d4c3`。当前环境仍没有四套 ComeOn.exe 与外传 Steam ComeOn.dll，所以深度 `verify_compatibility.py` 仍标记为待真实样本。
- **本体首轮实机最重要：继续使用 `BaseHeight=480`，优先测 `16:9` 和 `24:9`。** 日志中 `16:9` 应变成 `TargetWidth=856`，`24:9` 应保持 `1280`，并且 `stripe1目标宽度8像素对齐余数=0`。随后再复测 `32:9 / 8:9 / 40:9`。

- `layer1d` **不改变 layer1c 已实机通过的核心方案**。新增的只有“独立辅助面板短生命周期跟踪”：对象必须先在合法主菜单上下文中被识别并成功拥有动态 Draw wrapper，之后才记录“对象指针 + vtable + 本帧验证 epoch”。主 root 关闭以后，只要该对象仍在真实 `manager+0x1C -> object+0x08` Draw 链的 HUD 之前、仍 active、vtable 未变、有效矩形仍与 HUD 相交，就继续在 HUD 后绘制，并继续参与原版 picker 的单次 input-root 覆盖。

- **没有主菜单 active 时绝不发现新的未知对象。** layer1d 只允许继续保留此前已经由合法菜单上下文确认过的独立面板，所以不会因为普通跑图时某个窗口恰好与 HUD 相交就把它错误提升。
- 输入方案仍完全沿用 layer1c：只 Hook 原版顶层 picker 的单次返回值；`manager+0x40`、焦点、`+0x20/+0x24/+0x30`、child hit-test、按下/释放、键盘快捷键和按钮业务仍全部由原版处理。
- test1~test7 的 X/Y 位移、GetCursorPos 反算、`self+0xA8` 修补、`+0x30` 接管、按钮硬编码继续禁止；layer1b 的顶层链写入继续禁止。最右侧历史竖条纹仍单独处理，不属于本轮封版条件。

## 2026-09-15 layer1b 历史记录（实机失败，仅保留证据）

- layer1a 的实机剩余问题已经把根因闭合到 **Z 顺序不一致**：物品界面与 HUD 重叠区域的两个按钮可见但不可点；技能“连招编辑”子菜单的关闭按钮在重叠区同样不可点；另有左侧独立菜单/辅助面板仍可能被 HUD 压住。共同特征说明问题不是某几个 control ID，而是“视觉 Draw 已在 HUD 上面，原版反向输入链仍先命中 HUD”。
- layer1b 不再逐按钮修输入，也不再继续单纯延迟 Draw。它使用游戏自己已经存在的双向顶层 UI 链：`manager+0x1C=正向头`、`manager+0x18=反向尾`、`object+0x08=next`、`object+0x0C=previous`。正向链决定普通 Draw 次序，反向链决定顶层鼠标优先级；因此只要安全同步同一份 Z 顺序，视觉和输入会天然一致。
- 写链之前必须完整验证：头节点 previous 为 NULL、每个 next 的 previous 指回当前节点、正向最后一项等于 `manager+0x18`、尾节点 next 为 NULL、总项数不超过 128。任一条件失败时 **本帧零写入**，只记录一次警告并退回 layer1a Draw-only 兜底。
- 只有 `GAMEPLAY + CenterMainHUD=1 + AuxiliaryUIAboveHUD=1 + 至少一个 0x0B/0x0D/0x0E 主菜单 active` 才允许调整。候选必须原本位于 HUD 前方、处于 active，并且满足“主菜单本体 / parent 链能追到主菜单 / 有效矩形与 HUD 相交”之一；接近整屏的世界根/遮罩会被排除。
- 候选按原顺序组成稳定块插到 HUD 后面。这样正向 Draw 变成 `HUD -> 菜单/相关面板`，反向输入自然先访问菜单再访问 HUD；候选彼此顺序不颠倒，原本已经在 HUD 后面的更高层对象也不被抢位。
- layer1b **仍绝不修改** X/Y、`+0x58` 布局、child 树、active、`GetCursorPos`、`self+0xA8`、`+0x30` 命中、按钮业务函数、键盘快捷键，也绝不重新包装具有隐藏 ESI 语义的 `0x004B44F0`。test1~test7 的位移/输入补偿路线继续禁止回流。

## v0.3 封版使用与测试说明（历史稳定基线）
### 发行目录

`release\` 仍严格只有：

```text
DisplayFix.asi
DisplayFix.ini
```

### 首轮配置

先不要用 720/1080 混入性能变量：

```ini
[Display]
Enable=1
BaseHeight=480
AspectRatio=Auto

[Font]
FixDPI=1

[GUI]
CenterMainHUD=1
```

### 验收顺序

1. **冷启动到标题**：应是真正 640x480 4:3 源画布，由 cnc-ddraw 居中放大；此时不得出现 Strategy enter。
2. **进入游戏**：应出现 `Strategy enter state=3 GAMEPLAY profile=ready`，随后：

```text
[RUNTIME] Strategy enter original apply finished live=854x480 expected=854x480 force=1
```

3. 检查游戏内：底部 HUD 居中、小地图贴右、0x0B/0x0E 可点且不穿透、普通地图左键、右侧鼠标技能、Alt+F4。
4. **退出游戏回标题**：test15 已实机通过的关键日志为：

```text
[RUNTIME] Strategy exit old_state=3 FRONTEND profile=restored reset_mode=4 result=1 live=640x480 expected=640x480
```

5. 用户已确认标题重新回到和冷启动相同的 4:3 结构，不再保留 16:9 Surface。
6. v0.3 封版基线为 `BaseHeight=480 / AspectRatio=Auto`；600 仍是受支持的原生高度系，720/1080 只作为高 FOV/高负载实验。
7. `BaseHeight=1080` 已观察到严重掉帧，它不是 4K 输出模式；最终放大应交给 cnc-ddraw。

### 失败日志

如果退出时出现：

```text
[RUNTIME] Strategy exit FRONTEND force-reset FAILED; title may remain on gameplay surface
```

请保留完整日志。不要再测试 test11/test12 的 HUD/world gate；它们已经被实机否定。

## test11 基线正文（历史保留，当前结论以上方增补为准）

## 发行文件

正式 `release` 目录严格只有：

- `DisplayFix.asi`
- `DisplayFix.ini`

将两者放到游戏 ASI Loader 能加载的位置。插件运行后会在 ASI 同目录生成 `DisplayFix.log`。

## 推荐测试配置

```ini
[Display]
Enable=1
BaseHeight=720
AspectRatio=Auto

[Font]
FixDPI=1

[GUI]
CenterMainHUD=1
```

`BaseHeight` 是**游戏内世界逻辑高度**，不是主菜单分辨率。数值越大，世界可视范围越大，效果类似“缩远/FOV 增大”。

## v0.3-test11 的新测试目标

本版第一次把原游戏已经确认的“两套分辨率生命周期”正式拆开：

- 启动动画、前端、主菜单：保留原版固定 640x480 / 4:3 生命周期；
- 真正进入游戏并出现主 HUD 后：才启用 DisplayFix 的 `TargetWidth x BaseHeight`；
- 主 HUD 析构、准备回到前端时：恢复原版分辨率/JMM代码规则，让原游戏自己的 640x480 请求不再被动态分辨率补丁截走。

这样做是为了解决旧版在高 BaseHeight 下出现的典型错误：主菜单只画在左上角，右侧/下方大面积黑屏，甚至黑区中出现上一张动画或 3D surface 的黄色残影。

### 1. 启动动画与主菜单

从完全退出游戏开始启动。**不要先进入游戏再返回菜单**，先观察最初的前端。

预期：

- 动画/主菜单内容保持原生 4:3；
- cnc-ddraw 得到完整的原生前端画面后，按其输出设置等比放大并居中；
- 不应再出现“左上角只有一块 640x480 内容、剩余全黑”的情况；
- 不应再出现黑区中残留黄色赛道/场景/旧帧之类的 surface 污染。

说明：DisplayFix 不在前端阶段自行把 640x480 拉伸成 16:9。正确语义是**保留 4:3 源画布，再交给 cnc-ddraw 做最终等比缩放/居中**。因此 cnc-ddraw 自身应使用保持比例的输出设置。

### 2. 进入游戏

进入存档/新游戏，等底部主 HUD 真正出现。

预期日志会出现一次：

```text
[RUNTIME] gameplay resolution switch begin current=640x480(or 800x600) target=1280x720 mode=...
[RUNTIME] gameplay resolution switch end result=1 live=1280x720
```

若你使用 `BaseHeight=1080`，目标应相应为 `1920x1080`。

验收：

- 世界视野正确切到 BaseHeight 对应逻辑分辨率；
- 底部主 HUD 水平居中；
- 小地图和右侧按钮仍贴边；
- 属性/道具两个顶部按钮可正常打开；
- 点击属性/道具不让角色向下方地图坐标移动；
- 普通地图左键仍可移动；
- 右侧鼠标技能设置按钮正常；
- Alt+F4 正常退出。

### 3. Steam 版

Steam GUI 修复已经在 `v0.3-test10` 实机通过：Steam/ComeOn.dll 环境缺少的一次后续完整 JMM apply，会在 HUD/顶层 UI/资源根成熟后 one-shot 调用原版 `0x004B35F0` 补回。

进入游戏后应仍看到类似：

```text
[RUNTIME] Steam delayed JMM apply begin ...
[RUNTIME] Steam delayed JMM apply end result=1 done=1 child_layout_changed=1 ...
```

`test11` 新增的前端/gameplay profile 不得破坏这条 `test10` 稳定路径。

### 4. 返回主菜单

从游戏内正常返回主菜单，再观察一次。

预期：

- 主 HUD 析构时 DisplayFix 只恢复前端代码 profile，不在析构函数里强制 Reset；
- 日志应出现 `[RUNTIME] frontend resolution profile restored after HUD destruction; no forced display reset`；
- 原游戏随后请求主菜单 640x480 时应真正得到原生 640x480；
- 返回后的主菜单仍为完整 4:3 等比居中画面；
- 不出现旧的 TargetWidth 大 surface 黑区/残影。

### 5. 动画/过场回归

本版静态设计覆盖“没有主 HUD的前端/动画阶段”和“HUD 析构后返回前端”。请尽量观察：

- 启动 Logo/动画；
- 主菜单背景/过场；
- 从游戏返回主菜单时可能出现的过渡动画；
- 若游戏中存在会销毁主 HUD 的全屏动画，也请确认仍保持 4:3 等比显示。

如果发现某类动画是在主 HUD 仍存活时播放、却仍被当成游戏内动态分辨率，请记录具体触发位置；这说明还需要为该动画状态增加独立生命周期证据。

## 当前已实机通过的基线

- 96 DPI 字体路径：4K、Windows 125% 缩放下字体不再裁切；
- 任意 `BaseHeight` / fixed-Y + auto-X 世界分辨率；
- 非 Steam 高 BaseHeight GUI；
- 主 HUD 居中；
- 0x0B/0x0E 属性/道具按钮点击；
- 属性/道具点击穿透阻断；
- test8 对普通地图左键、Alt+F4 的回归修复；
- Steam `v0.3-test10` delayed full JMM apply，GUI 最终位置正确。

## 封版后仍保留的非阻塞后续项

- Steam 版帧数/游戏速度偏低问题仍可在下一阶段专项调查；v0.3 不修改 ComeOn.dll 性能路径。
- `AspectRatio=Auto` 目前仍读取显示器比例，不会自动跟随 cnc-ddraw 自定义客户区比例；用户已决定暂缓。
- 600/720/1080 等其它 BaseHeight 不作为本轮封版硬验收；其中 1080 已明确属于高负载内部世界模式。

出现异常时请保留完整 `DisplayFix.log`，并注明 Steam/非 Steam、BaseHeight、从哪个画面进入哪个画面。
