# 前端动画与主菜单研究说明（截至 v0.3.1）

## v0.3.1 同步说明

本轮不修改前端/游戏内显示生命周期。标题/主菜单继续使用原版 mode 4 / 640x480，进入 Strategy state 3 才切游戏内宽屏，退出后强制恢复 mode 4。唯一变化是：即使 `[Display] Enable=0`，`[Font] FixDPI=1` 仍可以独立修复字体。

---

## v0.3 封版结论：标题不做宽屏，恢复原游戏的 640x480 前端
用户已经提供了最重要的行为基准：**不加载 DisplayFix、只用历史宽屏 EXE 时，标题界面始终是 640x480；进入游戏后才应用设置的分辨率。** 因此当前不再把“标题与游戏内从始至终共享同一逻辑分辨率”当目标。

### test11～test14 排除链

- test11：主 HUD `+0x58` 自动布局在主菜单也发生，过早切宽屏；
- test12：world 对象在主菜单也存在，仍然过早；
- test13：Strategy state=3 gate 时机正确，但 `0x407000 -> 0x404D30` 的 `force=0` 因 mode ID 不变而早退；
- test14：进入 Strategy 临时 force=1 后，live 已实机正确切成 854x480；但退出仅恢复代码 profile，没有恢复 Surface，返回标题仍是宽屏并有旧 UI 残留。

### 原版启动前端的新反编译证据

```asm
004053D8  push ebx
004053D9  push 4
004053DB  mov  ecx,ebp
004053DD  mov  [ebp+08h],4
004053E4  call 00404D30
```

这证明原游戏自己明确把标题/前端置为 mode 4；标准样本 mode 4 即 640x480。

### test15 最终生命周期（已实机通过，v0.3 封版基线）

```text
进程启动/标题/主菜单
    FRONTEND profile + 原版 mode 4 = 640x480

Strategy state 3 enter
    GAMEPLAY profile
    0x407000 force 0 临时改 force 1
    原版 0x404D30 真正重建 TargetWidth x BaseHeight

Strategy state 3 exit
    先执行原版 0x407040 清理
    恢复 FRONTEND profile
    self+0x08 = 4
    原版 0x404D30(mode=4, force=1)
    live 必须回到当前 EXE 原 mode 4 宽高
```

因此前端的“居中放大”职责继续交给 cnc-ddraw：游戏只提供干净完整的 640x480 4:3 源画布。

test15 已实机得到完整闭环：

```text
Strategy enter original apply finished live=854x480 expected=854x480 force=1
Strategy exit old_state=3 FRONTEND profile=restored reset_mode=4 result=1 live=640x480 expected=640x480
```

用户确认返回主菜单恢复正常。因此“FRONTEND 原生 640x480 -> GAMEPLAY 宽屏 -> FRONTEND 640x480”不再是阻塞项，v0.3 以此封版。

## test11 基线正文（历史保留，当前结论以上方增补为准）

## 1. 原版架构结论

用户实机确认《刀剑封魔录》并不是“从进程启动到游戏内都共享一个逻辑分辨率”。至少存在两套生命周期：

- **前端/主菜单/启动动画**：原版固定使用 640x480，4:3；
- **游戏内**：进入世界以后才接受正式菜单中的 640x480 / 800x600 设置。

这条结论解释了旧版 DisplayFix 的高 BaseHeight 前端异常：如果 ASI 一加载就把原版三条分辨率分支全部改成 `1920x1080`，主菜单代码仍只按原生 640x480 资源/坐标绘制，于是只覆盖大 surface 的左上部分；未覆盖区域可能保持黑色，也可能暴露前一帧/其它 surface 的残留。

用户截图中的“左上角正常主菜单 + 大面积黑区 + 黄色赛道/场景残影”应作为该错误架构的固定反例，不允许回归。

## 2. 正确显示目标

前端不应该被改造成“真正的 16:9 菜单”。正确目标是：

1. 游戏继续生成完整的原生 640x480 4:3 前端画布；
2. 输出层保持长宽比；
3. 根据最终窗口/显示分辨率等比放大；
4. 画面居中；
5. 宽屏两侧留黑边（或由 cnc-ddraw 的既定比例策略处理），绝不横向拉伸资源；
6. 整个输出 surface 必须被正常清理/呈现，不能显示上一张 3D/动画 surface 残影。

DisplayFix 当前不重新实现一套 scaler，而是保证前端阶段不再被游戏内动态分辨率代码污染，让 cnc-ddraw 重新拿到正确 640x480 源画布。

## 3. v0.3-test11：双 profile 方案

### FRONTEND profile

保存并恢复当前 EXE 自己的原始代码立即数：

- 分辨率模式派发 `0x00404D7A` 中三条宽高；
- 第一处分辨率映射 `0x00470C3E`；
- 第二处分辨率映射 `0x0047B0AB`；
- JMM 选择器 `0x004B363B` 的 640/800 比较值。

“保存当前 EXE 原值”很重要：它不仅兼容完全原版，也不会在用户拿旧 480P/720P 等改版 EXE 测试时武断写回某套硬编码值。

ASI 初始化阶段只解析/保存这些位置，不写入 TargetWidth/TargetHeight。这样最初主菜单/动画保持原版生命周期。

### GAMEPLAY profile

主 HUD `vtable+0x58 -> 0x004B2B90` 第一次以 `(-1,-1)` 做自动布局时，说明游戏世界/HUD 已经建立。DisplayFix 此时：

1. 把三条模式分支统一成 `TargetWidth x BaseHeight`；
2. 同步两处分辨率映射；
3. 按 `BaseHeight < 600 / >=600` 配置 TargetWidth 对应 `JMMDL.txt / JMMDL800.txt`；
4. 读取显示对象 `0x00548398` 的 live Width/Height；
5. 若 live 尺寸尚不是目标，复用原版显示模式函数 `0x00404D30`，以当前模式 + `force=1` 重应用一次。

### 为什么切换后立即停止访问旧 HUD

`0x00404D30` 可能引发 DirectDraw 设备/Surface/UI 重建，当前 `self` 有可能在调用过程中析构。因此 hook 一旦真的触发显示模式重建，就立刻 return；重建出的新 HUD 会再次进入布局 hook，再完成居中和 Steam JMM 流程。

## 4. 返回主菜单

主 HUD vtable：`0x0052A7D4`。

- `+0x00`：scalar deleting destructor，当前样本目标 `0x004C2B50`；
- `+0x58`：布局，`0x004B2B90`。

v0.3-test11 hook `+0x00`。HUD 析构完成后，如果不是 DisplayFix 自己正在做 gameplay Reset，也不是 Steam delayed JMM 正在重载，就恢复 FRONTEND profile。

恢复成功时会写一条低频日志：`[RUNTIME] frontend resolution profile restored after HUD destruction; no forced display reset`。

这里**只恢复代码 profile，不强制调用 640x480 Reset**。理由：地图切换、读档等也可能临时析构 HUD；如果在析构函数里盲目 SetDisplayMode(640x480)，会把普通游戏流程也打断。真正返回菜单时，原游戏本来就会自己请求前端 640x480，我们只保证那次请求不再被 GAMEPLAY profile 改写。

## 5. 与 Steam v0.3-test10 的关系

Steam/ComeOn.dll 环境已经实机确认缺少一轮后续完整 JMM apply。test10 在游戏内 HUD 成熟后延迟调用一次原版 `0x004B35F0(0,TargetWidth,TargetHeight)`，并已实机得到：

```text
result=1
done=1
child_layout_changed=1
```

且 Steam 最终 HUD 坐标与非 Steam 第二阶段一致。

v0.3-test11 不能推翻这条已通过方案。代码使用：

- `g_gameplay_mode_switch_in_progress`
- `g_steam_ui_sync_in_progress`

互相防止 profile 重应用与 Steam JMM one-shot 在设备/UI 重建期间递归触发。

## 6. 已知边界

- `AspectRatio=Auto` 目前仍以显示器比例计算，不会自动读取 cnc-ddraw 自定义窗口客户区比例；用户明确暂缓。
- 本方案依赖“主 HUD 出现/析构”作为前端与游戏内的生命周期证据。若存在**HUD 不析构但播放固定 640x480 全屏动画**的场景，还需单独找到该动画的状态/入口，不能靠猜。
- 【历史状态】v0.3-test11 当时尚未实机验证；该方案后来被 test11 实机否定，最终由 test15 Strategy 生命周期替代并通过。

## 7. 本版验收清单

- 冷启动动画保持 4:3，等比居中放大；
- 最初主菜单保持 4:3，等比居中放大；
- 不再出现左上角小画面 + 巨大黑区；
- 不再出现黄色赛道/旧 surface 残影；
- 进入游戏时自动切到 TargetWidth x BaseHeight；
- HUD、属性/道具、地图左键、Alt+F4 全部无回归；
- Steam 仍完成 delayed full JMM apply；
- 从游戏返回主菜单时恢复 4:3 前端画面；
- 非 Steam 与 Steam 都要覆盖测试。
