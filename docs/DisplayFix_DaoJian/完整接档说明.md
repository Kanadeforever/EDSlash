## 0. v0.3.2 当前定位

`v0.3.2` 是当前正式源码/构建基线。它完整继承 v0.3.1 的运行逻辑，只把 `DisplayFix.log` 的等级、初始化说明、分辨率、HUD、输入和 Steam/JMM 诊断文本改为简体中文。

`v0.3.1` 的配置解耦仍然完整保留。外传移植测试曾暴露出一个本传同样存在但之前未覆盖的组合：`[Display] Enable=0` 时旧初始化会在字体补丁之前直接返回，因此即使 `[Font] FixDPI=1`，96-DPI 字体修复也不会执行。

v0.3.1 将初始化顺序固定为：**读取配置 -> 独立处理 FixDPI -> 再判断 Display.Enable -> Enable=1 时才继续宽屏/HUD/输入安装**。因此 `Enable=0 + FixDPI=1` 现在代表“完全保留原版显示结构，只启用字体 DPI 修复”。

本轮没有修改 v0.3 已实机通过的 Strategy enter/exit、force=1、FRONTEND mode 4、Steam delayed JMM、主 HUD 居中、0x0B/0x0E、world press 防穿透等运行时逻辑。v0.3 的 test15 实机结论继续是显示生命周期稳定基线。

### v0.3.1 新增构建防回归

`verify_build.py` 会静态确认 `if (config.fix_font_dpi)`、`apply_font_dpi_fix(&text_region)` 必须出现在 `if (!config.enable)` 之前；若以后重构重新耦合两个开关，构建验证直接失败。

## 0. 截至 v0.3 封版的当前定位

`v0.3` 以 test15 已实机通过的实现封版，不再尝试把标题界面本身做成宽屏。最终方案是**恢复游戏原始的两阶段显示生命周期**：

- 启动动画、标题、主菜单等 FRONTEND：真正使用原版 `mode 4 = 640x480` 的 4:3 Surface；
- 进入 Strategy/gameplay：才应用 `TargetWidth x BaseHeight`；
- 离开 Strategy：先让原版做完游戏内清理，再恢复 FRONTEND 机器码/JMM 规则，并强制以原版显示模式函数重建 `mode 4` Surface。

用户补充了一个非常重要的外部基准：**不加载 DisplayFix，仅使用历史“改 EXE 宽屏”方案时，标题界面无论游戏内设置为何都保持 640x480；只有进入游戏后才应用设置分辨率。** test15 按这一原版行为实现并已实机通过，v0.3 不再把“全程统一逻辑分辨率”作为目标。

## 1. test12 新增逆向与失败闭环

从已稳定的世界鼠标输入链继续闭合出 world 对象生命周期：

```text
world global                  0x00557D1C
构造函数写入全局             0x00473E20  mov [0x00557D1C], esi
scalar deleting destructor    0x00473E40
destructor 主体               0x00473E60
析构清空全局                 0x00473E8E  mov [0x00557D1C], ebx(0)
```

## 2. test13 新增 Strategy 高层状态机

`0x00404A00` 是已经闭合的高层状态切换函数，`self+0x0C` 保存当前状态。

进入新状态 3：

## 3. test13/test14：`0x00404D30` 的同-mode早退

显示模式函数 `0x00404D30` 在真正写宽高以前先检查当前 mode：

```asm

jne  apply
mov  ecx,[esp+1Ch]      ; force
 test ecx,ecx
je   return             ; mode 相同且 force=0：直接结束
```

这解释 test13 日志：GAMEPLAY profile 已写好，但 `live=640x480`。test14 只在原版 `0x00407000` 执行期间临时把 `6A 00` 的立即数改成 `01`，原函数返回后立即恢复。

用户 test14 实机已经给出决定性通过证据：

```text

[RUNTIME] Strategy enter original apply finished live=854x480 expected=854x480 force=1
```

所以 **Strategy enter 时机 + force=1 进入游戏路径已经闭合**。

## 4. test14 退出失败与 test15 新闭合

test14 退出日志只有：

```text

```

这句话只证明代码立即数/JMM selector 已恢复，不证明当前 DirectDraw Surface 已变回 640x480。用户实机显示：第一次标题是正确 4:3；进入游戏后宽屏正确；退出游戏后标题却落在仍然宽屏的 Surface 上，并残留小地图/技能 UI。

因此新增结论：

> **代码 profile 与 live display 是两个独立状态。恢复 FRONTEND profile 不会自动重建现有 Surface。**

### 4.1 新反编译：原版启动前端明确请求 mode 4

进一步反编译原游戏启动路径：

```asm
004053D8  push ebx               ; 当前路径 ebx=0，即 force=0
004053D9  push 4                 ; 原版明确请求 mode 4
004053DB  mov  ecx,ebp
004053DD  mov  [ebp+08h],4
004053E4  call 00404D30
```

而 `0x00404D30` 的原始模式分支已经确认：

```text

mode 5 -> 800x600
mode 6 -> 1024x768
其它/默认同样落到 640x480 分支
```

历史 480P～1080P 外部宽屏 EXE 改的是内部/扩展分支；这条启动前端 mode 4 路径仍保持一致。这与用户“改 EXE 宽屏时标题始终 640x480”的实机观察完全吻合。

### 4.2 test15 最终实现（v0.3 封版基线）

Strategy exit hook 现在严格按以下顺序：

1. 记录旧状态并清掉缓存 HUD；
2. 开启 `g_strategy_transition_in_progress`，先完整调用原版 `0x00407040`；
3. 原版 gameplay 清理结束后调用 `set_frontend_resolution_profile()`；
4. 从安装时保存的 `g_res_mode_original[4]/[5]` 取得当前 EXE 自己的 mode 4 原始宽高；标准样本即 640x480；
5. 模仿原版启动路径先写 `self+0x08=4`；
6. 调已签名验证的 `0x00404D30(self, mode=4, force=1)`；
7. 检查 `self+0x228 / self+0x22C` 是否真的等于原 mode 4 宽高；
8. 最后才解除 transition guard。

这里 `force=1` 同样是必要的，因为当前 mode ID 很可能仍然是 4；使用 0 会再次触发早退。

## 1. 当前版本定位

`v0.3-test11` 的新任务不是再改 Steam 游戏内 HUD，而是修复**前端/动画/主菜单被游戏内动态分辨率污染**的问题。

用户已经明确确认原游戏存在两套分辨率生命周期：

- 启动动画、主菜单等前端阶段固定逻辑 640x480、4:3；
- 真正进入游戏以后才接受游戏内 640x480 / 800x600 分辨率。

旧版 DisplayFix 在 ASI 初始化时就把三条分辨率分支统一到 TargetWidth x BaseHeight。高 BaseHeight 下，主菜单代码仍只按原生 640x480 绘制，于是出现：左上角一块正常菜单、其余大面积黑屏，甚至黑区显示黄色赛道/场景/旧帧 surface 残影。用户已给出截图，这个现象是 test11 必须消灭的直接回归样本。

本版因此引入 **FRONTEND / GAMEPLAY 两套运行时代码 profile**：

- FRONTEND：保持当前 EXE 自己的原始分辨率/JMM 规则，让前端继续真正生成完整 640x480 4:3 画布，再交给 cnc-ddraw 等比放大和居中；
- GAMEPLAY：主 HUD 真正出现后才启用 TargetWidth x BaseHeight，并必要时复用原版 `0x00404D30` 重应用当前显示模式；
- 主 HUD 析构时恢复 FRONTEND profile，但不在析构函数里粗暴强制一次 640x480 Reset。

**test11 当前只有静态逆向、内容签名、编译验证；前端/动画 profile 尚未用户实机通过，不能标成稳定基线。**

## 3. v0.3-test11 前端/gameplay profile 架构

### 3.1 初始化阶段只解析，不提前扩分辨率

`apply_dynamic_resolution()` 现在只：

- 找到分辨率模式派发；
- 找到两处分辨率映射；
- 保存**当前 EXE 自己的原始立即数**；
- 从 `0x00404D7A` 向前解析并验证原版显示模式函数 `0x00404D30`；
- 保存 TargetWidth / TargetHeight。

`apply_jmm_layout_selection()` 也只解析 `0x004B363B` 并保存原始 640/800 比较值。

初始化结束时调用 `set_frontend_resolution_profile()` 做一次自检，确保代码仍保持原值。

保存“当前 EXE 原值”而不是写死原版数字，目的是继续兼容用户已有 480P/720P 等历史改版样本。

### 3.2 FRONTEND profile

恢复：

- `0x00404D7A` 模式派发中 6 个宽高立即数；
- `0x00470C3E` 第一处分辨率映射；
- `0x0047B0AB` 第二处分辨率映射；
- `0x004B363B` JMM 640/800 比较值。

结果：原游戏前端请求 640x480 时不再被 DisplayFix 改成 1280x720 / 1920x1080。这样 cnc-ddraw 获得完整 640x480 4:3 源画布，可以在最终窗口中保持比例居中放大。

### 3.3 GAMEPLAY profile

主 HUD `vtable+0x58` 第一次真实自动布局 `(-1,-1)` 之后调用 `activate_gameplay_resolution_if_needed()`：

1. 先写 GAMEPLAY profile；
2. 三条模式分支全部统一到 TargetWidth x TargetHeight；
3. 两处分辨率映射同步 TargetWidth/TargetHeight；
4. BaseHeight<600：TargetWidth 走 `JMMDL.txt`；
5. BaseHeight>=600：TargetWidth 走 `JMMDL800.txt`；
6. 读取显示对象当前 live Width/Height；
7. 若 live 已经是目标，不 Reset，只保持 profile；
8. 若不是目标，读取当前 mode 4/5/6，复用原版 `0x00404D30(display,current_mode,force=1)` 重应用一次。

显示模式重应用可能销毁/重建 HUD，所以触发后 layout hook 立即返回，绝不继续访问旧 `self`。

### 3.4 返回前端

主 HUD vtable `+0x00` 的 scalar deleting destructor 被内容结构验证后 hook。当前样本指向 `0x004C2B50`，函数头是：

```text
56 8B F1 E8 ...
```

析构完成后，只要不是 DisplayFix 自己正在进行 gameplay display Reset，也不是 Steam delayed JMM 正在重载，就：

- 清当前 HUD 实例；
- 恢复 FRONTEND profile；
- 成功后限次记录 `frontend resolution profile restored after HUD destruction; no forced display reset`，用于实机确认返回菜单生命周期。

这里**不直接 SetDisplayMode(640x480)**，因为地图切换/读档也可能临时析构 HUD。真正返回主菜单时由原游戏自己的前端流程请求 640x480。

## 12. 构建规范

`build.bat`：UTF-8 **无 BOM** + CRLF；即使首行已有 `chcp 65001 >nul` 也禁止 BOM。头部和 PROJECT_ROOT 写法按用户固定规范；所有有正文的 REM/echo 行末尾两个 ASCII 空格。

LLVM 查找只允许：PATH -> `%ProgramFiles%\LLVM\bin` -> `vswhere` 最新 VS `VC\Tools\Llvm\x64\bin`。禁止递归 `where /r`、禁止 ARM64 LLVM、clang/lld-link 同目录。
