# DisplayFix v0.3-test11 完整接档说明

## 1. 当前版本定位

`v0.3-test11` 的新任务不是再改 Steam 游戏内 HUD，而是修复**前端/动画/主菜单被游戏内动态分辨率污染**的问题。

用户已经明确确认原游戏存在两套分辨率生命周期：

- 启动动画、主菜单等前端阶段固定逻辑 640x480、4:3；
- 真正进入游戏以后才接受游戏内 640x480 / 800x600 分辨率。

旧版 DisplayFix 在 ASI 初始化时就把三条分辨率分支统一到 TargetWidth x BaseHeight。高 BaseHeight 下，主菜单代码仍只按原生 640x480 绘制，于是出现：左上角一块正常菜单、其余大面积黑屏，甚至黑区显示黄色赛道/场景/旧帧 surface 残影。用户已给出截图，这个现象是 test11 必须消灭的直接回归样本。

本版因此引入 **FRONTEND / GAMEPLAY 两套运行时代码 profile**：

- FRONTEND：保持当前 EXE 自己的原始分辨率/JMM 规则，让前端继续真正生成完整 640x480 4:3 画布，再交给 cnc-ddraw 等比放大和居中；
- GAMEPLAY：主 HUD 真正出现后才启用 TargetWidth x BaseHeight，并必要时复用原版 `0x00404D30` 重应用当前显示模式；
- 主 HUD 析构时恢复 FRONTEND profile，但不在析构函数里粗暴强制一次 640x480 Reset。

**test11 当前只有静态逆向、内容签名、编译验证；前端/动画 profile 尚未用户实机通过，不能标成稳定基线。**

## 2. 已实机确认的稳定基线

以下结论在 test11 中必须保持，不允许回归：

- 96 DPI 字体修复：4K + Windows 125% 缩放、不启用高 DPI 缩放替代时，右上角 `v 1.05` 等文字完整显示；
- fixed-Y / auto-X 世界分辨率成立，`BaseHeight` 任意正整数；
- INI 第一节 BOM 问题在 test8a 修复，test8b 日志确认 BaseHeight=720 能正确读出并计算 1280x720；
- v0.2-test1 底部主 HUD 视觉居中，用户评价“非常完美”；
- 非 Steam 高 BaseHeight GUI 主线从 v0.3-test1 起正常；
- 属性/道具真实 control ID 为 `0x0B / 0x0E`；
- test6 起两个窗口可打开；
- test8 起普通地图左键、Alt+F4 恢复，属性/道具点击不再穿透导致角色移动；

## 3. v0.3-test11 前端/gameplay profile 架构

### 3.1 初始化阶段只解析，不提前扩分辨率

`apply_dynamic_resolution()` 现在只：

- 找到分辨率模式派发；
- 找到两处分辨率映射；
- 保存**当前 EXE 自己的原始立即数**；
- 从 `0x00404D7A` 向前解析并验证原版显示模式函数 `0x00404D30`；
- 保存 TargetWidth / TargetHeight。

`apply_jmm_layout_selection()` 也只解析 `0x004B363B` 并保存原始 640/800 比较值。

初始化结束时调用 `set_frontend_resolution_profile()` 做一次自检，确保代码仍保持原值。

保存“当前 EXE 原值”而不是写死原版数字，目的是继续兼容用户已有 480P/720P 等历史改版样本。

### 3.2 FRONTEND profile

恢复：

- `0x00404D7A` 模式派发中 6 个宽高立即数；
- `0x00470C3E` 第一处分辨率映射；
- `0x0047B0AB` 第二处分辨率映射；
- `0x004B363B` JMM 640/800 比较值。

结果：原游戏前端请求 640x480 时不再被 DisplayFix 改成 1280x720 / 1920x1080。这样 cnc-ddraw 获得完整 640x480 4:3 源画布，可以在最终窗口中保持比例居中放大。

### 3.3 GAMEPLAY profile

主 HUD `vtable+0x58` 第一次真实自动布局 `(-1,-1)` 之后调用 `activate_gameplay_resolution_if_needed()`：

1. 先写 GAMEPLAY profile；
2. 三条模式分支全部统一到 TargetWidth x TargetHeight；
3. 两处分辨率映射同步 TargetWidth/TargetHeight；
4. BaseHeight<600：TargetWidth 走 `JMMDL.txt`；
5. BaseHeight>=600：TargetWidth 走 `JMMDL800.txt`；
6. 读取显示对象当前 live Width/Height；
7. 若 live 已经是目标，不 Reset，只保持 profile；
8. 若不是目标，读取当前 mode 4/5/6，复用原版 `0x00404D30(display,current_mode,force=1)` 重应用一次。

显示模式重应用可能销毁/重建 HUD，所以触发后 layout hook 立即返回，绝不继续访问旧 `self`。

### 3.4 返回前端

主 HUD vtable `+0x00` 的 scalar deleting destructor 被内容结构验证后 hook。当前样本指向 `0x004C2B50`，函数头是：

```text
56 8B F1 E8 ...
```

析构完成后，只要不是 DisplayFix 自己正在进行 gameplay display Reset，也不是 Steam delayed JMM 正在重载，就：

- 清当前 HUD 实例；
- 恢复 FRONTEND profile；
- 成功后限次记录 `frontend resolution profile restored after HUD destruction; no forced display reset`，用于实机确认返回菜单生命周期。

这里**不直接 SetDisplayMode(640x480)**，因为地图切换/读档也可能临时析构 HUD。真正返回主菜单时由原游戏自己的前端流程请求 640x480。

## 4. Steam 路径：test10 已通过，test11 不得破坏

Steam/ComeOn.dll 环境缺少非 Steam 自然发生的一轮完整后续 JMM apply。

失败路线：

- test9：只广播 34 个顶层 UI 的 `vtable+0x14`，全部 applied 但 child 坐标不变；
- test4：ASI 初始化阶段过早重放完整 `0x004B35F0`，弹 `MB\JMMDL*.txt`。

正确路线 test10：等 HUD 0x0B/0x0E、顶层 UI 链、资源根都成熟后，Steam one-shot 调：

```text
0x004B35F0(0, TargetWidth, TargetHeight)
```

用户 BaseHeight=1080 Steam 实机确认：

- before 0x0B ≈ x1132，0x0E ≈ x1160；
- after 0x0B ≈ x1288，0x0E ≈ x1316；
- `result=1 / done=1 / child_layout_changed=1`；
- GUI 截图位置正确。

test11 用 `g_gameplay_mode_switch_in_progress` 与 `g_steam_ui_sync_in_progress` 防止 gameplay Reset 和 Steam JMM one-shot 互相递归。

## 5. 输入链稳定方案

### 5.1 属性/道具真实按钮

主 HUD vtable `+0x24 -> 0x004C3E40`。

实机 A/B 日志已确认：

- `0x0B`：属性/道具顶部按钮之一，目标窗口全局槽 `0x00559274`；
- `0x0E`：另一个顶部按钮，目标窗口全局槽 `0x0055BDC8`；
- active：`0x004B1DB0`；
- 切换窗口：目标对象 `vtable+0x1C(!active,0)`。

### 5.2 释放 fallback

全局 release callsite：

```text
0x00406086 -> 0x004B4560
```

原版 UI dispatch 永远先执行。只有鼠标命中实时 0x0B/0x0E 矩形、且目标窗口 active 状态没有被原版改变时，DisplayFix 才补一次原版式 toggle。

### 5.3 点击穿透

禁止 hook/wrap `0x004B44F0`。test7 已实机导致：

- 普通地图左键不能移动；
- Alt+F4 失效。

根因：`0x004B44F0` 内部直接使用调用者保留的 ESI 作为下游虚函数隐藏上下文，普通 C wrapper 无法安全保留该语义。

当前只在：

```text
0x004060EB -> 0x00473F10
```

这个真正世界输入 callsite 上判断实时 0x0B/0x0E 矩形；命中才跳过本次世界移动，其它地图位置原样调用世界函数。

## 6. DPI 字体修复

关键链：

```text
0x004B438E GetDeviceCaps(LOGPIXELSY)
0x004B439F MulDiv
0x004B43A5 neg eax
0x004B43EE CreateFontIndirectA
```

局部把 DPI 查询等长替换为固定 96，不改整个进程 DPI；永久脚本位于 `source\FontFix_DaoJian\`，按目标机器码/上下文验证，不锁整文件 SHA-256。

## 9. Steam 文件结构

Steam EXE 主体与非 Steam 几乎一致，仅少量字节构造启动桩，在 `0x00527CD0` 附近通过原 EXE IAT `LoadLibraryA` 加载 `ComeOn.dll`，再回原启动流程。

`ComeOn.dll` 导入 Steam API、线程/窗口/GDI/VirtualProtect/Read/WriteProcessMemory 等。QPC/GetTickCount 当前追到的是 CRT security-cookie，尚无证据可直接当帧率限制器 patch。

Steam 帧数/游戏速度偏低是 test11 前端验证之后的下一高优先级专项。

## 12. 构建规范

`build.bat`：UTF-8 BOM + CRLF；头部和 PROJECT_ROOT 写法按用户固定规范；所有有正文的 REM/echo 行末尾两个 ASCII 空格。

LLVM 查找只允许：PATH -> `%ProgramFiles%\LLVM\bin` -> `vswhere` 最新 VS `VC\Tools\Llvm\x64\bin`。禁止递归 `where /r`、禁止 ARM64 LLVM、clang/lld-link 同目录。
