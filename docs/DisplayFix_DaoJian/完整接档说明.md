# DisplayFix v0.3-test10 完整接档说明

## 当前版本定位

`v0.3-test10` 以 `v0.3-test8b` 的输入、BaseHeight、DPI、非 Steam GUI 与 test8 输入链为稳定基线。test9 的 Steam 专用“只广播顶层 `vtable+0x14`”已经由实机判定失败：日志明确显示 `visited=34 / applied=34 / done=1`，但真实顶部按钮 `0x0B / 0x0E` 的 before/after 坐标完全不变，GUI 仍停留在错误的第一阶段布局。重新反汇编 `0x004B35F0` 后确认，非 Steam 自然第二阶段在广播之前还会通过 `0x004EB9E0` 构造 `mb\` 路径并由 `0x004D0500` 重新加载 `JMMDL.txt/JMMDL800.txt`。test10 因此只在 Steam/ComeOn.dll 环境、HUD/顶层 UI/资源根目录都成熟后，补调用一次完整原版 `0x004B35F0(mode=0, TargetWidth, TargetHeight)`；不改 `0x4087B5` 自然 callsite，非 Steam 完全不执行额外调用。

### 已实机确认的稳定事实

- DPI 字体修复有效：4K + Windows 125% 缩放、不启用高 DPI 缩放替代时，文字完整显示。
- 固定 Y / 自动 X 的世界分辨率方案成立；`BaseHeight` 可自由调整，可作为类 FOV / 世界缩放参数。
- `v0.2-test1` 的底部主 HUD 视觉居中已被用户确认“非常完美”。
- 非 Steam GUI 从 v0.2-test1 起就是正常主线；高 BaseHeight 在 v0.3-test1 后非 Steam 也正常。
- 属性/道具真正的两个顶部按钮是 `0x0B / 0x0E`。
- `v0.3-test6` 在 BaseHeight=720 下已确认两个按钮可以打开，而且没有 v0.3-test1 的右侧鼠标技能按钮回归。

### v0.3-test7 为什么废弃

虽然 test7 阻止了按钮点击导致角色移动，但同时：

- 普通地图左键不能移动角色；
- Alt+F4 不能关闭游戏。

日志证明普通地图点击并没有被错误标成 consume=1。反汇编进一步发现 `0x004B44F0` 会使用调用者保留的 ESI 作为下游虚函数的隐式输入，普通 C wrapper 会改变调用原函数那一刻的寄存器上下文。因此 test7 的全局 press wrapper 必须整体撤销，不能修修补补继续用。

### v0.3-test8 的唯一新实验

保留原版：

```text
0x004060CD -> 0x004B44F0
```

只 hook：

```text
0x004060EB -> 0x00473F10
```

如果世界输入真正准备执行时，鼠标位于当前主 HUD ID 0x0B / 0x0E 的实时矩形，就只跳过本次 `0x473F10`；其它位置原样调用。窗口开关仍由 test6 已成功的 release fallback 完成。

## v0.3-test10 当前必须实机验收

1. Steam：`BaseHeight=720`，进入游戏后不手工切分辨率；日志应出现一次 `Steam delayed JMM apply begin/end`。
2. Steam：理想结果为 `result=1`、`done=1`、`child_layout_changed=1`，并且 `0x0B/0x0E` after 坐标进入非 Steam 第二阶段位置。
3. Steam：不得弹出 `MB\JMMDL.txt` / `MB\JMMDL800.txt`；如果出现，立即退出并保留日志。
4. Steam：观察帧数/游戏速度。test9 已将高频 WORLD/GLOBAL 普通点击日志关闭，test10 继续保持低日志量。
5. 非 Steam：不得执行任何 `Steam delayed JMM apply`；GUI 继续保持此前正常。
6. 两边输入快速回归：普通地图左键、属性/道具不穿透、右侧鼠标技能设置、Alt+F4。

### test9 为什么失败

- test9 触发条件正确，Steam 下 `manager+0x1C` 已成熟，实际遍历 34 个顶层对象并成功调用 34 次 `vtable+0x14`。
- 但 `id0B_before == id0B_after`、`id0E_before == id0E_after`，截图也确认 GUI 仍错误。
- 因此“非 Steam 的第二阶段 = 纯尺寸广播”这一假设被实机否定。

### test10 Steam 修复安全边界

- 运行条件：检测到 `ComeOn.dll`。
- 触发时机：主 HUD `0x0B/0x0E` 已建立，`manager+0x1C` 顶层链非空，且从 `0x4B35F0 -> 0x4EB9E0` 解析出的游戏资源根目录字符串已经非空。
- 动作：只额外调用一次原版 `0x4B35F0(0, TargetWidth, TargetHeight)`，让 JMM 资源加载与后续 UI 广播都走原版完整流程。
- one-shot：`in_progress` 防递归；原版返回非 0 后 `done=1`，本进程不再重复。
- 禁止：改写 `0x4087B5` 自然 JMM callsite、恢复 test7 的 `0x4B44F0` wrapper、让非 Steam 进入 Steam 分支。
- test4 的“ASI 初始化阶段直接重放完整 0x4B35F0”仍然是失败方案；test10 与其关键差异是增加“HUD/顶层链/资源根目录均成熟”的延迟门槛。

## 当前架构

- 主插件：Win32/x86 `DisplayFix.asi`
- 零 Import Directory；运行所需 Win32 API 尽量复用 ComeOn.exe IAT，无法直接复用的通过其 `GetProcAddress` 取得。
- EXE 兼容性按机器码/上下文签名判断，不锁整体 SHA-256。
- 发行目录只允许：`DisplayFix.asi`、`DisplayFix.ini`。

- `verify_build.py` 新增 build.bat 自检：禁止 `where /r`、禁止 ARM64 LLVM 路径、要求存在 x64 VS LLVM 回退，并检查 UTF-8 BOM + CRLF 以及所有有正文的 `REM` / `echo` 行末尾两个半角空格。
- test8b 后续实机日志已经确认 INI 第一节修复成立：Steam 与非 Steam 都能正确读取 `BaseHeight=720` 并计算 `1280x720`；这一项不再是阻塞。
