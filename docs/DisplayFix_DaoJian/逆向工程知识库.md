## 2. 字体 / DPI 路径

### 2.1 根因

游戏字体高度会用 Windows 当前 DPI 计算，但文字格、布局和裁切区域仍按 96 DPI 设计。在 125%、150% 等 DPI 下字体被放大，导致例如右上角 `v 1.05` 等文本被裁切。

已闭合调用链：

- `0x004B438E`：`GetDeviceCaps(..., LOGPIXELSY)`
- `0x004B439F`：`MulDiv(...)`
- `0x004B43A5`：`neg eax`
- `0x004B43EE`：`CreateFontIndirectA`
- `GetDeviceCaps` IAT：`0x0052805C`（机器码 `FF 15 5C 80 52 00`）

### 2.2 已通过修复

原 6 字节：

```asm
call dword ptr [GetDeviceCaps]
```

等长替换为：

```asm
add esp, 8
push 96
pop eax
```

机器码：`83 C4 08 6A 60 58`

原因：原 API 是 `stdcall`，原调用会自行清理两个参数；替换后必须手工 `add esp,8`，否则栈会错位。

实机通过条件：4K、Windows 125% DPI、取消“高 DPI 缩放替代”，字体显示正常，并可与宽屏 EXE / cnc-ddraw 共存。

独立永久补丁工具位于 `source\FontFix_DaoJian\`。它不再锁整个 EXE SHA-256，而是检查目标机器码与上下文；因此能兼容未修改该字体路径的其它改版 EXE。

## 3. 分辨率与世界视野

### 3.1 游戏菜单实际可选分辨率

正式游戏设置界面只确认有：

- `640x480`
- `800x600`

程序内部还残留一条 `1024x768` / 扩展分支，但它不是菜单里可选择的第三个槽位。早期把它描述成菜单槽位是错误结论。

### 3.2 关键地址

- 分辨率模式派发：`0x00404D7A`
- 第一处分辨率映射：`0x00470C3E`
- 第二处分辨率映射：`0x0047B0AB`
- 原内部/扩展分支默认值：`1024x768`

外部宽屏 EXE 样本把该扩展分支改成：

- 854x480
- 960x540
- 1280x720
- 1366x768
- 1600x900
- 1920x1080

这些样本证明游戏能接受非原生逻辑分辨率，但纵向分辨率越高，世界可见范围也越大，所以直接 1920x1080 会“看得过远”。

### 3.3 DisplayFix 当前设计

逻辑高度由用户 `BaseHeight` 决定，宽度按宽高比自动算：

```text
TargetHeight = BaseHeight
TargetWidth  = round(BaseHeight * AspectWidth / AspectHeight)
```

`BaseHeight` 不设人为上限，只要求正整数；它本质上也是世界缩放 / 类 FOV 参数：

- 数值更大：看得更多，画面缩远
- 数值更小：看得更少，画面拉近

`AspectRatio=Auto` 读取输出/桌面比例；也允许任意手工 `W:H`，不设置 16:9/21:9 白名单。因此 5:4、3:2、16:10、32:9 等都走同一公式。

极少数比 4:3 更窄的比例允许主 HUD 少量裁切，不为此缩放或重排 GUI。

## 4. JMM / GUI 布局系统

### 4.1 两套已确认布局模板

- `JMMDL.txt`：480 系 / 640 参考宽度
- `JMMDL800.txt`：600 系 / 800 参考宽度

布局文件选择器：`0x004B363B`

当前 DisplayFix 规则：

- `BaseHeight < 600` -> 走 `JMMDL.txt` / 640 参考宽
- `BaseHeight >= 600` -> 走 `JMMDL800.txt` / 800 参考宽

注意：这只是 GUI 模板分界，不会把世界高度截断回 480/600。例如 `BaseHeight=720` 仍然是真正 720 高世界视野。

### 4.2 分辨率重新应用包装

- 包装函数：`0x004087A0`
- 读取对象 `+0x228` / `+0x22C` 的 Width / Height
- `0x004087B5` 调 `0x004B35F0`
- `0x004B35F0` 不只是广播尺寸，还会在前半段拼接 `mb\` + `JMMDL*.txt` 并重新加载资源，然后遍历顶层 UI 调 `vtable+0x14(mode,width,height)`。

因此“启动后直接重放整个 `0x004B35F0`”不是安全的轻量重排：v0.3-test4 实机出现 `MB\JMMDL.txt` / `MB\JMMDL800.txt` 弹窗，该路线已废弃。

### 4.3 非 Steam GUI 已知基线

用户回溯确认：

- v0.2-test1 时非 Steam GUI 就已经正确。
- v0.3-test1 开始支持更高 BaseHeight 后，非 Steam GUI 也仍正确。

因此非 Steam 主线不需要额外 startup JMM/UI rebroadcast。test3~test5 对启动重建的实验不应继续进入非 Steam 运行路径。

### 4.4 Steam 第二阶段布局缺失：test9 失败与 test10 修正

BaseHeight=720 的 test8b 运行日志：

- Steam 与非 Steam 第一次：`0x0B≈812,633`、`0x0E≈840,634`。
- 非 Steam 后续自然第二阶段：`0x0B≈968,632`、`0x0E≈996,633`，其它 HUD 同步重新定位。
- Steam 没有后续阶段。

#### test9：只广播尺寸，已实机失败

test9 从 `0x4087A0` 内容签名解析 UI manager（当前样本 `0x0055AF98`），等待 `ComeOn.dll`、主 HUD 0x0B/0x0E、`manager+0x1C` 顶层链成熟后，遍历 34 个顶层对象并调用：

```text
object->vtable+0x14(mode=0, TargetWidth, TargetHeight)
```

Steam 实机日志明确为 `visited=34 / applied=34 / done=1`，但 `id0B_before == id0B_after`、`id0E_before == id0E_after`，截图中的 GUI 也保持错误布局。因此“第二阶段 = 纯尺寸广播”这一假设被否定。

#### 重新闭合 0x004B35F0 的完整顺序

`0x004B35F0` 的前后半段现在拆清：

- `0x004B360E`：`call 0x004EB9E0`，构造当前游戏资源根目录 + `mb\`。
- `0x004B363B`：按 width 判断 `640 / 800 / 1024`，DisplayFix 会把比较值动态改成当前 `TargetWidth` 对应模板。
- `0x004B3649 / 0x004B3664`：选择 `JMMDL.txt` 或 `JMMDL800.txt` 字符串。
- `0x004B369D`：`call 0x004D0500`，ECX=`0x0055AE70`，真正加载选中的 JMM 布局资源。
- `0x004B36A2` 起：取 `manager+0x1C` 顶层链，逐个调用 `vtable+0x14(mode,width,height)`。

因此非 Steam 的第二阶段本质是：**JMM 资源重新加载 + 顶层 UI 尺寸广播**。

#### 0x004EB9E0 / 资源根目录

已确认 `0x004EB9E0` 函数头：

```asm
56
57
BF 68 01 56 00      ; EDI = 0x00560168，游戏资源根目录缓冲区
83 C9 FF
33 C0
...
```

它把 `0x00560168` 的游戏资源根目录复制到临时缓冲区，再追加字符串 `mb\`（常量位于 `0x0054629C`）。最终返回临时路径缓冲区 `0x0056028C`。

这条信息用于 test10 的安全门槛：只有资源根目录字符串已经非空时，Steam 才允许补完整 JMM apply。

#### test10：延迟完整原版 JMM apply

Steam one-shot 条件：

1. 检测到 `ComeOn.dll`；
2. 主 HUD 真实 child `0x0B/0x0E` 已建立；
3. `manager+0x1C` 顶层链非空；
4. 从 `0x4B35F0 +0x1E -> 0x4EB9E0` 解析出的资源根目录缓冲区已经非空；
5. 当前没有正在进行的 Steam JMM apply。

满足后只执行一次：

```text
0x004B35F0(manager, mode=0, TargetWidth, TargetHeight)
```

`in_progress` 防止内部广播触发主 HUD layout 时递归；原版返回非 0 后 `done=1`，进程内不再重复。非 Steam 完全不走这条额外调用。

#### test4 与 test10 的区别

test4 也曾在 ASI 初始化阶段直接重放完整 `0x4B35F0`，结果弹 `MB\JMMDL.txt / MB\JMMDL800.txt`。现已确认这是**调用时机太早**的失败实验，不能简单归纳为“完整 0x4B35F0 永远不能调用”。test10 增加 HUD、顶层链和资源根目录三重成熟条件，目标是复用非 Steam 自然阶段的同一原版入口。

## 5. 主 HUD 对象与通用 UI 结构

### 5.1 主 HUD 根类

- 构造位置：`0x004C2AE3`
- vtable：`0x0052A7D4`
- `vtable + 0x24` -> `0x004C3E40`：主 HUD 鼠标/事件处理
- `vtable + 0x30` -> `0x004A1F90`：命中更新路径
- `vtable + 0x58` -> `0x004B2B90`：通用布局函数

### 5.2 已确认对象字段偏移

主 HUD / child 共用的关键字段：

- `+0x08`：next child
- `+0x14`：X
- `+0x18`：Y
- `+0x1C`：Width
- `+0x20`：Height
- `+0x28`：Control ID
- `+0x64`：active A
- `+0x68`：active B
- `+0x9C`：直属 child 链头
- `+0xA0`：原版遍历/迭代指针
- `+0xA8`：当前命中 child
- `+0xB8`：active/latch 相关字段

通用命中：`0x004B3380`

active 查询：`0x004B1DB0`

`0x004B3380` 自己会通过 ComeOn.exe 的 `GetCursorPos` IAT `0x005283C8` 读取游戏所见的鼠标坐标。兼容 cnc-ddraw 时应尽量复用游戏 IAT，而不是盲用桌面坐标。

### 5.3 HUD 居中算法

v0.2-test1 已实机确认视觉“非常完美”。算法只移动底部主 HUD 根对象，不动小地图和左右边缘顶层 UI。

```text
centerDelta = (TargetWidth - NativeBaseWidth) / 2
```

NativeBaseWidth：

- BaseHeight < 600 -> 640
- BaseHeight >= 600 -> 800

布局 hook 对 `(-1,-1)` 自动布局先调用一次原版，再以 `originalX + centerDelta`、原 Y 调第二次原版布局，因此 child 与点击区域在绝大多数正常控件上会一起更新。

边缘 UI 继续贴边，这是设计目标，不应整体挤到中间。

## 6. 属性 / 道具顶部两个按钮

这是整个宽屏输入问题里最难的部分，已经通过多轮失败方案逐步闭合。

### 6.1 真正 Control ID

v0.3-test4 在 `CenterMainHUD=0` 的纯诊断实机日志确认：

- 顶部按钮之一 -> `ID 0x0B`
- 顶部按钮之二 -> `ID 0x0E`

早期误判为 `0x0F / 0x10` 是错误。

720 高、HUD 居中后的示例实时矩形：

- 0x0B：约 `968,632 - 986,650`
- 0x0E：约 `996,633 - 1014,651`

命中矩形只有约 18x18，视觉圆形图案比矩形大；这是游戏自己的控件设计，不是 DisplayFix 新增。

### 6.2 原版窗口开关链

主 HUD `vtable+0x24 = 0x004C3E40` 中：

- `ID 0x0B` 使用目标窗口全局槽 `0x00559274`
- `ID 0x0E` 使用目标窗口全局槽 `0x0055BDC8`
- 两条分支都调用 `0x004B1DB0` 查询目标窗口 active
- 最终通过目标对象 `vtable+0x1C(!active, 0)` 开/关窗口

### 6.3 为什么普通 HUD 按钮没问题、这两个有问题

HUD 根节点视觉居中后，大多数普通 child 的输入随布局正常更新；但 0x0B/0x0E 的事件在宽屏状态下会在更高层 UI 路由里漏掉，导致鼠标释放不一定进入主 HUD 的 `+0x24`。因此在 HUD 内部继续修 `self+0xA8` 太晚。

### 6.4 v0.3-test6 成功路径

主循环释放链：

```text
0x00406070 ...
0x00406086 CALL 0x004B4560  ; UI manager 全局 mouse release
```

DisplayFix 在这个全局释放层：

1. 读取当前主 HUD 实例的 0x0B/0x0E 实时矩形；
2. 原版 `0x004B4560` 永远先执行；
3. 如果原版没有改变对应目标窗口 active，DisplayFix 才复用原版 `target->vtable+0x1C` 开关；
4. fallback 成功时 release 返回 handled=1。

用户在 BaseHeight=720 实机确认：属性/道具终于可以打开，右侧鼠标技能设置按钮也没有 v0.3-test1 的回归。

### 6.5 点击穿透与 test7 失败根因

虽然 test6 能开窗口，但同一次点击还会让角色向按钮下方地图坐标移动。按下链为：

```asm
004060CD  call 004B44F0    ; UI 按下分派
004060D2  test eax,eax
004060D4  jne  004060F0
004060D6  mov  ecx,[00557D1C] ; 世界对象
...
004060EB  call 00473F10    ; 世界按下/角色移动路径
```

v0.3-test7 尝试包装 `0x004B44F0` 并在命中 0x0B/0x0E 时把返回值改成 handled=1。表面日志看起来普通地图点击 `consume=0`，但实机却出现：

- 普通地图左键完全不能移动角色
- Alt+F4 也不能退出游戏

进一步反汇编确认 `0x004B44F0` 存在非标准隐式寄存器依赖：它会把调用者保留的 ESI 在内部直接 `push esi` 传给下游 `vtable+0x20`。调用者在 `0x00406058` 从 IAT `0x005283CC` 载入 ESI，并在后续路径保留。普通 C `__fastcall` wrapper 虽会遵守 ABI 最终恢复 ESI，但在“wrapper 内部再次调用原 0x4B44F0”的瞬间，ESI 已不保证还是原调用者值，因此语义被破坏。

结论：**绝不能再包装 0x004B44F0。**

### 6.6 v0.3-test8 新方案

test8 恢复完整原版 `0x004B44F0` 路径，只 hook 真正的世界输入 callsite：

- callsite 区域：`0x004060D6`
- CALL：`0x004060EB`
- 原目标：`0x00473F10`
- 世界对象：`[0x00557D1C]`
- 栈参数仍为 event_type / mouse_x / mouse_y
- `0x00473F10` 最终 `ret 0x0C`

`0x00473F10` 函数头会保存 EBX/EBP/ESI/EDI，并立即 `mov esi,ecx`；目前没有观察到像 `0x004B44F0` 那样依赖调用者旧 ESI 的隐藏输入。

test8 逻辑：

- mouse_x/y 落在当前 0x0B/0x0E 实时矩形 -> 只跳过本次 `0x00473F10`
- 其他任何位置 -> 原样调用 `0x00473F10`
- 窗口开关仍由 test6 的 release fallback 完成

实机状态：test8 已确认修复 test7 的普通地图左键 / Alt+F4 回归，属性/道具也继续能响应；该输入链现作为 test8a 的稳定运行时基线。

## 7. 主循环输入相关地址

已确认区域：

- `0x00405FB0` 一带：鼠标坐标读取/主输入准备区域
- `0x00406070`：release callsite 签名起点
- `0x00406086 -> 0x004B4560`：UI manager mouse release
- `0x004060B7`：press UI callsite 上下文起点
- `0x004060CD -> 0x004B44F0`：UI manager mouse press；**存在隐藏 ESI 语义，禁止普通 C wrapper**
- `0x004060D6`：UI press 未处理后进入世界输入的上下文起点
- `0x004060EB -> 0x00473F10`：世界鼠标按下 / 角色移动路径
- `0x004060F0`：按下阶段状态继续点
- `0x00406058`：`mov esi,[0x005283CC]`，后续 `0x4B44F0` 会使用调用者保留的 ESI
- `0x005283C8`：`GetCursorPos` IAT
- `0x005283CC`：按键状态相关 IAT；API 名称尚未在本项目中完全固化，但其寄存器值对 `0x4B44F0` 路径有实际语义

## 8. 主界面 / Frontend 分辨率架构

用户确认原游戏主界面与游戏内是两套分辨率方案：

- 主界面固定逻辑 `640x480`
- 真正进入游戏后才接受 640x480 / 800x600 等游戏内分辨率调整

当前 DisplayFix 修改游戏逻辑分辨率后，主界面可能只把 640x480 内容画在左上角，剩余区域黑屏。

未来正确目标不是把主界面也改成 BaseHeight 世界分辨率，而是：

1. 主界面仍保持 640x480 / 4:3 原生画布；
2. 根据实际输出窗口大小等比放大；
3. 居中显示；

## 9. Steam / 非 Steam 行为差异

### 非 Steam

- v0.2-test1 起 GUI 已正确。

### Steam

- GUI 布局异常
- 游戏速度明显拖慢

## 10. 已确认失败方案，禁止重复

1. **全局 SHA-256 锁 EXE**：失败于兼容性设计。正确做法是目标机器码/上下文签名验证。
2. **v0.2-test2：mouseX-centerDelta 后重新扫描 child**：属性/道具仍无效。
3. **v0.3-test1：把误判的 0x0F/0x10 child X 临时平移后跑原 hit-test**：两个按钮仍无效，并让非 Steam 右侧鼠标技能设置按钮不能点击。
4. **v0.3-test2：按视觉矩形后补 `self+0xA8`**：无效。
5. **v0.3-test3：把 0x0F/0x10 当作目标并直接分派**：ID 认错，路线无效。
6. **test4：ASI 初始化阶段立即完整重放 `0x4B35F0`**：资源根/GUI 时序未成熟，弹 `MB\JMMDL*.txt`；“过早重放”失败，不等于正确时机调用永远失败。
7. **在主 HUD `+0x24` 之后补窗口**：事件本身可能根本没有被路由到 HUD，层级太晚。
8. **v0.3-test7 包装 `0x4B44F0` 并改 handled**：严重失败；普通地图左键失效、Alt+F4 失效。根因是隐藏 ESI 输入语义。
9. **v0.3-test9 只广播顶层 `vtable+0x14`**：34 个对象全部实际调用成功，但 0x0B/0x0E 坐标完全不变，GUI 仍错误；缺失的是 JMM 资源加载 + 广播的完整阶段。
