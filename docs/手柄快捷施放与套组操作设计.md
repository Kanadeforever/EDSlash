# 手柄快捷施放与套组操作设计

日期：2026-10-01。状态：新布局尚未修改运行时代码。用户已取消 X/Y 长按选择，已选定 LT 组合方案一；下文第三、七、八节保留调查过程，第九节为当前操作候选。

## 一、新方向

原版技能与 F1..F6 投掷采用“选择到右手，再按右键”的流程，不适合继续原样搬到手柄。用户要求：技能和投掷快捷组合直接请求发动效果；Y 专门执行四套自定义连招，不能再被任意技能或投掷选择覆盖。

“直接发动”省去右手选择和额外按 Y 的步骤。执行资格、物品数量、消耗、硬直与原生动作限制仍由业务层判断；本轮不顺带扩大预输入或取消窗口。

## 二、拟定操作分工

| 操作 | 新职责 |
|---|---|
| X 短按 | 当前左手动作，通常为普攻 |
| Y 短按/连按 | 当前选中自定义套组的下一步 |
| RT+已配置技能键 | 直接请求对应技能，不把它长期改成 Y 的动作 |
| RB+ABXY/左右 | 直接请求对应六槽投掷，不要求再按 Y，也不变成同槽取消 |
| LB 药品快捷 | 继续直接使用，不因本轮改变 |
| 长按 Y 后给方向 | 在四套自定义连招之间选择 |
| 长按 X 后给方向 | 作为左手动作选择菜单的同类交互；候选范围需尊重原版允许左手绑定的动作 |

长按门槛可配置。选择输入设备可配置为十字键、左摇杆或右摇杆；默认映射可沿用已有的上/右/下/左对应 1/2/3/4，但具体默认与提交时机尚未冻结。

选择层只消费所指定设备的方向输入，不能穿透为打开属性/技能界面、移动角色或发动战斗动作。RT/LB/RB/LT 的组合层优先处理其中的 X/Y，不应因此触发基础 X/Y 的长按选择。选择时需要明确显示当前项目和候选，不能仅写日志让玩家盲选。

## 三、必须先确定的短按/长按冲突

共用同一个动作键时，系统在刚按下的一刻无法知道玩家随后会短按还是长按：

1. 按下立即发动，继续按住达到门槛再打开选择：保留即时战斗响应，但门槛前会先发动动作；按当前按住连发逻辑，门槛到来前可能已发动多次，不能保证仅一次。
2. 松开且未到门槛才发动，达到门槛只打开选择：长按不会误发动，但短按延迟到松开才生效。

已向用户提出这一核心问题，当前推荐保留按下即响应，明确告知长按前会发动动作，现有连发可能使门槛前不止一次。用户要求先核实原版是否需要按住技能，故暂不冻结该选择；调查结果见下节。

此前“X/Y 长按为位置型动作展开目标点”的未实现设计也与新长按菜单有占键冲突。后续必须明确迁移到技能快捷层或另设操作，不能在 X/Y 长按中同时执行两种业务；本轮不自行冻结该细节。

## 四、两版原生接口核对

### 四套连招可以按编号独立读取

本体 `0x4C4A70`、外传 `0x4D9050` 接受明确索引 0..3 时返回对应列表；只有传 -1 才依赖当前右手选择字段。列表头保存数量/首末节点，节点 +0x08 保存原版选择数据。

因此 Y 可以持有独立的选中套组与进度，不再通过“当前右手 getter”决定自己执行什么。快捷技能与投掷的成功通知不能推进 Y 的套组游标。只在真正的套组步骤成功建立时推进。

### 原版投掷快捷执行器不能直接当作直投接口

两版十二槽执行器：本体 `0x4C3CA0`、外传 `0x4D8260`。

- 前六槽调用物品使用业务。
- 后六槽将对应物品切入右手，并设置投掷选择状态。
- 再次按已选的同一投掷槽会取消选择，恢复上一右手动作。

原版右手读取还有投掷专门分支：在对应类别与槽有效时，从物品 +0x20 生成 `值+10000` 的特殊选择码；数量 +0x1C 必须有效。因而不能只拿通用投掷招式 ID，也不能简单“调用旧快捷执行器后再调用 Y”。

下一步应沿具体逻辑槽解析物品，核对物品专用选择码、执行与扣除数量的链，再创建直接投掷请求。物品消耗完、槽被移动或重复选择时，都不能污染 Y 的套组状态。

## 五、实现侧需要拆开的状态

当前只有“左手/右手”不足以描述这些新来源，至少需要：

- 左手常规动作；
- 自定义套组步骤；
- 快捷技能；
- 指定槽位投掷；
- 药品直接使用。

每个动作请求保留自己的来源、选择、目标与有效期。实际成功通知根据来源更新对应状态：快捷技能/投掷不改套组选中项、不递增套组进度；套组切换与编辑也不得使旧请求误推进新套组。

原有技能解析、原生提交和动作历史中的战斗规则可复用，但要分清“原生技能序列历史”和“手柄 Y 的自定义套组进度”，不能把它们合成一个计数器。

## 六、尚未实施

当前 release 仍为 dev5，Y 仍按旧右手动作逻辑，RT/RB 仍是选择后另行发动。本文是新设计的接档，不代表新布局已可使用。两作必须同时实现并验证，移动手感和已暂定的短缓冲不在本轮调整范围。

## 七、原版按住状态调查（2026-10-01）

两份准确散列基线均存在“标志有效时，检查右键是否按住，松开请求结束”的条件代码；具体实际技能是否启用，不能仅凭消费分支认定，后续加载顺序修正见第八节。Method 子记录中存在首字段类型 4 时，本体派生 +0x98 标志，外传派生 +0x9D 标志；这不是 +0x43 子型字段。角色更新只对活动动作的上述标志非零时检查 GetAsyncKeyState(VK_RBUTTON)，松开后构造原始动作 15 包；接收方写 Runtime+0x467，后续运行时更新在允许条件下结束动作。

普通世界按钮的松开回调不能代表这条轮询路径。当前 Game_Async 在普通手柄模式把鼠标键状态统一返回 0，因此具备上述标志的动作可能被原版视为已松开。此缺口未被现有替身回放覆盖，也不能把目前已测普通连招正常当作所有持续技能正常。

当前资料只有 EXE 和逆向文档，未找到实际 Skill.ini、Skill.gop 及子记录资源正文，具体玩家技能名单尚未对应完成；不能据此断言是某个名称的技能，也不能把请求结束一概解释为蓄力释放。新快捷技能需保留自身按下、持续、松开来源，并通过明确的业务状态/结束事件处理；不能全局伪造右键按住而重新打开鼠标攻击路由。X/Y 长按菜单方案仍待此条件纳入后决定。

## 八、X/Y 长按影响调查与结论修正（2026-10-01，基于 138eae9）

本节是研究结论，不代表已新增操作或修复运行时；用户正在测试的 release 保持不变。

### 1. 条件分支不等于实际技能已经启用

双版本技能记录构造器先把子记录计数及指针清零。本体 0x4D6510、外传 0x4EB980 的标准首次加载路径随后调用固定字段解析（0x4D62A0 / 0x4EB6E0），解析末尾调用标志派生 helper（0x4D6180 / 0x4EB5E0）；此时子记录计数仍是 0，因此该次 +0x98 / +0x9D 派生结果为 0。固定字段解析返回后，加载器才读取子记录数量、分配每条 0x20 字节的数组并加载子记录；已核对的函数返回前没有再次派生。

在两份可执行节中扫描 rel32 直接调用，派生 helper 分别只有 0x4D64EF / 0x4EB967 一处候选，均是上述提前调用；未发现 helper 地址被作为完整常量函数指针引用。该扫描不排除所有间接修改或其它外部数据写入，不能升级为“全游戏绝无长按技能”，但足以撤销“已证明实际存在需要按住的玩家技能”的强结论。

目前确认的是条件性结束代码存在，以及标准首次加载不启用该标志；没有确认任何具体玩家技能必须长按，也没有确认蓄力松开发动。前文 Game_Async 的影响必须限定为“若运行时实际启用了此标志，则会把其视为已松开”，不能写成用户当前普通战斗必然被该机制中断。实际名单和活跃标志仍未实机读取，亦未向游戏附加调试器。

初始化、字段解析、完整首次加载函数已加入 trace_native_actions.py 的可重复证据导出；当前每作 16 组函数范围与 4 组基本块，经准确散列和完整指令范围校验通过。

### 2. 当前 X/Y 的确定语义

- Control_Step 只在刚按下时产生 pressed；持续按住产生 held，没有 X/Y 长按门槛，也没有 X/Y 松开事件业务。
- Combat_Update 在新按下时立即请求动作；继续按住且无活动动作、无待重试请求时，自动创建下一次动作请求。因此按住 X 可连续普攻，按住 Y 可继续旧右手动作/预设推进；这是重复请求，不是把一个技能一直保持活动。
- 动作活跃时，普通 held 不会每帧重发；新按另一键则仍可立即进入原版资格/窗口判断。两键都按住时以最新明确按下边沿选择左右手，不能在菜单设计中破坏已修复的 X/Y 交替。
- 松开只阻止新的 held 连发；此前短缓冲可以继续到其剩余期限内。现有测试已经覆盖“松开后暂时不可用的动作恢复资格时执行”和期限耗尽后丢弃，故不能把松开当成清空所有已排队动作。
- 按住 X/Y 会让 Game_Update 进入攻击分支，不再发摇杆移动；摇杆仍参与方向及目标选择。RT/LB/RB 等切层会屏蔽此前已按住的键，返回基础层时须松开重按。这是输入路由保护，不是真实物理松键。

### 3. 长按菜单的冲突

| 设计 | 已确认影响 |
|---|---|
| 达到门槛就自动接管 X/Y 并开菜单 | 持续攻击会在门槛处变成选择；门槛前可能已出多次动作，而不是保证先出一次 |
| 松开才决定是否短按发动 | 所有点按都会延迟，X/Y 交替和窗口时机需要重调；若有真正持续技能，无法在按住阶段起动 |
| 按下立即发动，达到门槛后再收到指定方向才切组 | 保留连续攻击；明确选择手势才接管，仍须处理方向穿透、旧缓冲与松键锁定 |

当前推荐第三项，尚未由用户冻结。长按达到门槛本身只使切组手势可用；可以显示非阻断的候选提示，但不能自动停止攻击或进入输入独占。真正给出选择方向时再消费该方向与选择键，选择后不要把仍按住的 X/Y 自动当成一次新攻击，须先松键再恢复该键。不得强制取消已发动动作来掩盖缓冲或菜单状态问题。

默认更适合十字键：左摇杆同时用于移动/指向，在持续攻击中转向会很常见，作为选择输入更容易误切；右摇杆也需要先检查未来瞄准功能占用。用户要求的十字键/左摇杆/右摇杆配置选择仍可保留，但指定设备的语义和冲突必须明确。

选择输入必须在 Game_Keyboard 注入 C/V/N/B 和 Game_Update 更新朝向/目标之前消费，不能到了世界业务阶段才发现已打开原版页面。进入选择后清掉手柄尚未提交的旧重试；已被原版接受的待执行动作需要核对来源归属后处理，不能粗暴清空共享状态。

### 4. 将来若确认有持续技能

维持状态应归属实际发动该动作的按键和请求，不使用“X 或 Y 任意一个仍按着”的总布尔值。独立保存角色/世界、实际 Runtime、来源按钮、动作及执行序号，区分待请求、原版待执行与已经活动的生命周期。否则 X 发动后再按 Y，可能错误地让 Y 维持 X 的旧动作，或松开 X 时误结束 Y 的新动作。

RT+某键直接施放后，不能只从 LAYER_GAME 的 held 判断是否还按住；层级屏蔽与物理松开是两件事。失焦、断线、切图、切入鼠标模式也需要明确清理自有持续状态。只对当前受控角色的自有动作处理，不修改共享 Method 标志，也不全局伪造右键按住；原版条件分支究竟需要在哪个入口做来源隔离，须在实际活跃标志确认后落实。

## 九、取消 X/Y 长按选择，改用 LT 组合（2026-10-01 当前候选）

用户决定不再把选择菜单绑定到 X/Y 长按。这里取消的是长按选择，不自行删除现有按住连续攻击。X 执行当前左键动作，Y 专用当前自定义套组；RT 直接技能、RB 直接投掷、LB 药品的方向继续保留。LT 防御及配合左摇杆方向闪避继续保留；两方案都使用 LT+ABXY 处理四个必杀技槽，首次按下选择/确认，再次按相同键请求释放，换键改选，不因持续按住自动确认第二次。

| 操作 | 方案一 | 方案二 |
|---|---|---|
| LT+十字键上下左右 | 四套自定义连招直接切换 | 选择左键动作 |
| LT+右摇杆上下左右 | 打开左键动作菜单并导航 | 四套自定义连招直接切换 |
| LT+ABXY | 必杀技选择与同键二次释放 | 相同 |
| LT+左摇杆 | 原定方向闪避；菜单独占时暂停闪避输入 | 原定方向闪避；需明确左键选择界面独占 |

用户已选择方案一。四套连招数量固定，与十字键四方向能建立稳定对应；左键候选需按角色已学且允许左键绑定的动作生成，可能多于四项，更适合有明确焦点的列表导航。方案二右摇杆可以切四套，但左键候选若按四方向直接映射就有数量上限；若十字键也作为菜单导航，则仍要另定打开、持续显示及松开确认的生命周期，不能认为无需菜单。

方案一的左键菜单采用用户明确的流程：按住 LT 后拨动右摇杆才打开；保持 LT 时持续显示；摇杆回中仍保留菜单与当前焦点；右摇杆上下左右导航；松开 LT 确认焦点对应的左键动作并关闭。确认是改变 X 的动作选择，不是自动发动该动作，不改 Y 套组或快捷技能。

实现必须具备以下边界，尚未生成代码：

- 十字键切套组只响应新的方向输入，不每帧反复切换。四方向与套组对应可配置，并显示当前套组反馈。
- 右摇杆菜单保留焦点；导航需要自身的方向判定、回中和长推重复节奏，不能把每帧轴值都算一次选择，也不能改动已暂定的左摇杆移动手感。
- 菜单打开时独占选择输入，禁止同时触发套组切换或 LT+ABXY 必杀业务；为避免边看菜单边闪避，推荐保留原有防御但暂不消费左摇杆为闪避。打开前 LT+左摇杆仍按原定职责。
- LT+ABXY 第一按只确认选择，第二次必须是同一键的新按下边沿。换键重新确认；推荐松开 LT、打开左键菜单、切场景、失焦或断线时清除未释放的必杀确认，避免下一次组合意外释放。实际释放仍走原版业务资格和消耗判断，不模拟鼠标轨迹。
- 原版防御与选择/必杀同属 LT；菜单不应每帧重新发起防御，实际必杀释放需允许原生动作按正常规则接管。方向闪避与必杀此前仍未实现，不能写成当前发布包已经支持。
- 选择方向在键盘页快捷和世界方向业务之前消费；松开 LT 的确认帧不能同时泄漏成基础攻击。用户正在测试的 release 保持不变，方案一已经冻结；用户明确 LT+右摇杆原生左键弹出菜单留到最后，本轮不实现菜单。

## 十、本轮落实与菜单后置

用户明确左键菜单就是原版左键 GUI 点击后弹出的那个，按住 LT 后拨右摇杆才打开，保持 LT 显示和防御，松开 LT 选中。菜单实现留到最后；不能另造四项轮盘或把本轮防御实现当成菜单已完成。现有 Game_Menu 会阻断世界动作，后续必须为自有原生左键菜单增加受控例外，保持防御并隔离闪避/必杀。
