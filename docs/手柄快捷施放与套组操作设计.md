# 手柄快捷施放与套组操作设计

日期：2026-09-30。状态：用户提出的新操作方向与实现评估，尚未修改运行时代码。用户要求先调查原版长按技能，再决定短按/长按触发时机，不能按推荐项自动视为同意。

## 一、新方向

原版技能与 F1..F6 投掷采用“选择到右手，再按右键”的流程，不适合继续原样搬到手柄。用户要求：技能和投掷快捷组合直接请求发动效果；Y 专门执行四套自定义连招，不能再被任意技能或投掷选择覆盖。

“直接发动”省去右手选择和额外按 Y 的步骤。执行资格、物品数量、消耗、硬直与原生动作限制仍由业务层判断；本轮不顺带扩大预输入或取消窗口。

## 二、拟定操作分工

| 操作 | 新职责 |
|---|---|
| X 短按 | 当前左手动作，通常为普攻 |
| Y 短按/连按 | 当前选中自定义套组的下一步 |
| RT+已配置技能键 | 直接请求对应技能，不把它长期改成 Y 的动作 |
| RB+ABXY/左右 | 直接请求对应六槽投掷，不要求再按 Y，也不变成同槽取消 |
| LB 药品快捷 | 继续直接使用，不因本轮改变 |
| 长按 Y 后给方向 | 在四套自定义连招之间选择 |
| 长按 X 后给方向 | 作为左手动作选择菜单的同类交互；候选范围需尊重原版允许左手绑定的动作 |

长按门槛可配置。选择输入设备可配置为十字键、左摇杆或右摇杆；默认映射可沿用已有的上/右/下/左对应 1/2/3/4，但具体默认与提交时机尚未冻结。

选择层只消费所指定设备的方向输入，不能穿透为打开属性/技能界面、移动角色或发动战斗动作。RT/LB/RB/LT 的组合层优先处理其中的 X/Y，不应因此触发基础 X/Y 的长按选择。选择时需要明确显示当前项目和候选，不能仅写日志让玩家盲选。

## 三、必须先确定的短按/长按冲突

共用同一个动作键时，系统在刚按下的一刻无法知道玩家随后会短按还是长按：

1. 按下立即发动，继续按住达到门槛再打开选择：保留即时战斗响应，但长按选择前会先发动一次动作。
2. 松开且未到门槛才发动，达到门槛只打开选择：长按不会误发动，但短按延迟到松开才生效。

已向用户提出这一核心问题，当前推荐保留按下即响应，明确告知长按会先发动一次。用户要求先核实原版是否需要按住技能，故暂不冻结该选择；调查结果见下节。

此前“X/Y 长按为位置型动作展开目标点”的未实现设计也与新长按菜单有占键冲突。后续必须明确迁移到技能快捷层或另设操作，不能在 X/Y 长按中同时执行两种业务；本轮不自行冻结该细节。

## 四、两版原生接口核对

### 四套连招可以按编号独立读取

本体 `0x4C4A70`、外传 `0x4D9050` 接受明确索引 0..3 时返回对应列表；只有传 -1 才依赖当前右手选择字段。列表头保存数量/首末节点，节点 +0x08 保存原版选择数据。

因此 Y 可以持有独立的选中套组与进度，不再通过“当前右手 getter”决定自己执行什么。快捷技能与投掷的成功通知不能推进 Y 的套组游标。只在真正的套组步骤成功建立时推进。

### 原版投掷快捷执行器不能直接当作直投接口

两版十二槽执行器：本体 `0x4C3CA0`、外传 `0x4D8260`。

- 前六槽调用物品使用业务。
- 后六槽将对应物品切入右手，并设置投掷选择状态。
- 再次按已选的同一投掷槽会取消选择，恢复上一右手动作。

原版右手读取还有投掷专门分支：在对应类别与槽有效时，从物品 +0x20 生成 `值+10000` 的特殊选择码；数量 +0x1C 必须有效。因而不能只拿通用投掷招式 ID，也不能简单“调用旧快捷执行器后再调用 Y”。

下一步应沿具体逻辑槽解析物品，核对物品专用选择码、执行与扣除数量的链，再创建直接投掷请求。物品消耗完、槽被移动或重复选择时，都不能污染 Y 的套组状态。

## 五、实现侧需要拆开的状态

当前只有“左手/右手”不足以描述这些新来源，至少需要：

- 左手常规动作；
- 自定义套组步骤；
- 快捷技能；
- 指定槽位投掷；
- 药品直接使用。

每个动作请求保留自己的来源、选择、目标与有效期。实际成功通知根据来源更新对应状态：快捷技能/投掷不改套组选中项、不递增套组进度；套组切换与编辑也不得使旧请求误推进新套组。

原有技能解析、原生提交和动作历史中的战斗规则可复用，但要分清“原生技能序列历史”和“手柄 Y 的自定义套组进度”，不能把它们合成一个计数器。

## 六、尚未实施

当前 release 仍为 dev5，Y 仍按旧右手动作逻辑，RT/RB 仍是选择后另行发动。本文是新设计的接档，不代表新布局已可使用。两作必须同时实现并验证，移动手感和已暂定的短缓冲不在本轮调整范围。

## 七、原版按住状态调查（2026-10-01）

两份准确散列基线均确认存在按住右键维持、松开请求结束的机制。Method 子记录中存在首字段类型 4 时，本体派生 +0x98 标志，外传派生 +0x9D 标志；这不是 +0x43 子型字段。角色更新只对活动动作的上述标志非零时检查 GetAsyncKeyState(VK_RBUTTON)，松开后构造原始动作 15 包；接收方写 Runtime+0x467，后续运行时更新在允许条件下结束动作。

普通世界按钮的松开回调不能代表这条轮询路径。当前 Game_Async 在普通手柄模式把鼠标键状态统一返回 0，因此具备上述标志的动作可能被原版视为已松开。此缺口未被现有替身回放覆盖，也不能把目前已测普通连招正常当作所有持续技能正常。

当前资料只有 EXE 和逆向文档，未找到实际 Skill.ini、Skill.gop 及子记录资源正文，具体玩家技能名单尚未对应完成；不能据此断言是某个名称的技能，也不能把请求结束一概解释为蓄力释放。新快捷技能需保留自身按下、持续、松开来源，并通过明确的业务状态/结束事件处理；不能全局伪造右键按住而重新打开鼠标攻击路由。X/Y 长按菜单方案仍待此条件纳入后决定。
