## 1. 当前定位

`BladeSwordQOL v0.1-dev1` 是《刀剑封魔录》系列大修/QoL 项目的第一版统一架构基线。它把此前分开的本体 DisplayFix 与《刀剑封魔录外传：上古传说》DisplayFix 合并为 **一个 Win32/x86 ASI**：

```text
BladeSwordQOL.asi
BladeSwordQOL.ini
```

同一个 ASI 会先识别当前主程序属于本体还是外传，再只初始化匹配的 Profile 后端。当前正式功能模块为 `DisplayFix` 与 `QOL`。2026-09-27 用户将当前阶段调整为 Controller 独立开发与测试，未来再合并；Controller 仍是本项目子模块，源码必须位于 `source\src\Modules\Controller\`，文档、工具和产物沿用项目现有目录。

本版本的核心目标是“架构迁移与共享 Hook 基础设施”，不是重新设计已经实机闭合的 DisplayFix。原有本体/外传后端仍作为两个独立 C 翻译单元存在，以尽量保持运行逻辑等价；统一 Runtime 提供唯一入口、游戏识别、模块注册、共享 Hook 所有权、事件总线、Win32 API 桥和 x86 detour。

## 2. 当前实机结论

### 2.1 本体 DisplayFix

已由用户实机确认：

- `layer1c` 解决了物品/技能重叠区域“看得见但点不到”的问题；

## 3. AspectRatio 8 像素规则

这条规则属于 `[Display] AspectRatio` 的统一宽度求值，不是 Auto 专项，也不是独立 StripeFix 模块。

流程固定为：

```text
取得比例
  ├─ AspectRatio=Auto：从桌面/输出取得比例
  └─ AspectRatio=W:H：使用用户手工比例
        ↓
理想宽度 = BaseHeight × W / H
        ↓
选择距离理想宽度最近的 8 像素倍数
        ↓
TargetWidth
```

`BaseHeight=480` 时已知样本：

| 比例 | 旧宽度 | 8 对齐宽度 | 旧版竖条状态 | 新版实机状态 |
|---|---:|---:|---|---|
| 16:9 | 854 | 856 | 有 | 已确认消失 |
| 32:9 | 1708 | 1704 | 有 | 尚未复测 |
| 8:9 | 428 | 424 | 有 | 尚未复测 |
| 40:9 | 2134 | 2136 | 有 | 尚未复测 |
| 24:9 | 1280 | 1280 | 无 | 天然对照组 |

当前证据高度支持“最终 Surface/横向路径需要 8 像素对齐”，但严格说目前只对 16:9 新算法完成了实机闭合；其它奇葩比例建议之后抽测一组即可。

## 4. 新统一架构

```text
source/
├─ build.bat / build_controller.bat / readme.md
├─ src/
│  ├─ Main.c
│  ├─ Runtime/
│  │  ├─ Runtime / GameProfile / HookManager
│  │  ├─ EventBus / ModuleRegistry
│  │  └─ Win32Bridge / X86Detour
│  └─ Modules/
│     ├─ DisplayFix/（两作后端）
│     ├─ QOL/（名称、分类、拾取）
│     └─ Controller/（当前独立 ASI）
├─ config/
├─ tools/
└─ vendor/SDL3/
```

### 4.1 唯一入口

主插件目标只有 `source\src\Main.c` 可以定义：

- `DllMain`
- `InitializeASI`

两个 Profile 后端都不再拥有 DLL/ASI 入口。

### 4.2 GameProfile

Runtime 在访问任意 Profile 专用 IAT 地址之前，先直接读取主 EXE PE32 头：

- 本体：`SizeOfImage=0x00173000`，`AddressOfEntryPoint=0x0010F0EF`
- 外传：`SizeOfImage=0x001A5000`，`AddressOfEntryPoint=0x00127BCF`

匹配成功后才进入对应后端。后端内部仍继续执行原有内容签名验证，因此 PE 身份只是第一层保护，不取代深度验证。

### 4.3 ModuleRegistry

主插件当前注册顺序为 DisplayFix、QOL；Controller 当前独立产出，未注册到主插件。Registry 保存初始化入口返回值并继续后续模块，不因一个可选模块返回失败而终止全部模块。

ModuleRegistry_IsInitialized 是入口返回状态，不是每个物理补丁均成功的证明。两个 DisplayFix 后端在有效句柄下调用内部初始化后返回 1，内部 patch 失败另行记录日志；不能据 Registry 状态宣称所有显示功能成功。

### 4.4 HookManager / EventBus

`HookManager` 建立“一个物理游戏 Hook 只能有一个提供者”的硬规则。当前 DisplayFix 仍负责安装它已经实机验证过的物理 Hook，以避免本轮大范围重写；但这些公共入口已经登记到共享 Hook 管理体系。

Hook 声明还增加了初始化回滚：如果一个模块已经 Claim 了前几个共享 Hook、后面的 Claim 却发生冲突，必须通过 `HookManager_ReleaseOwned()` 清理尚未安装入口的 owner；已写入口必须先完整撤销，撤销失败则保留 owner，不能留下“模块没启动但 Hook 被占住”的假状态。

当前已广播的第一批语义事件：

- `RUNTIME_EVENT_GAMEPLAY_ENTER`
- `RUNTIME_EVENT_GAMEPLAY_EXIT`
- `RUNTIME_EVENT_UI_DRAW_BEGIN`
- `RUNTIME_EVENT_UI_DRAW_END`

未来合并的手柄模块若需要这些生命周期，应订阅 EventBus。当前独立目标不能把主插件内部 EventBus 当成跨 DLL 接口，也不允许直接重复覆盖 DisplayFix 的 Strategy/UI Draw。

注意：**v0.1-dev1 是共享 Hook 基础设施的第一阶段，不代表所有 DisplayFix 物理 Hook 已经搬进 Runtime。** 当前采用“稳定后端继续装 Hook + Runtime 接收语义事件”的保守迁移方式；以后真正出现第二模块共享同一入口时，再把那个入口的物理安装器上提到 Runtime。
