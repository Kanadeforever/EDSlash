# 《刀剑封魔录外传：上古传说》DisplayFix v0.1-test2 完整接档说明

## 1. 版本定位

这是外传非 Steam 主线的第二个测试版。v0.1-test1 已经由用户在非 Steam 版实机确认绝大多数核心功能正常，并且用户顺带在 Steam 版上测试后也确认大部分功能正常。v0.1-test2 不改变已经通过的宽屏生命周期、HUD、输入或字体机器码方案，只修复一个配置层错误：`[Display] Enable=0` 时不应连带关闭 `[Font] FixDPI=1`。

当前主线目标仍然是先把非 Steam 版完整稳定化；Steam 版只登记现象和顺带验证结果，cnc-ddraw OpenGL 在开场动画结束后闪退的问题最后再单独调查。

## 2. v0.1-test1 实机结论

用户已经分别测试非 Steam 版和 Steam 版。非 Steam 版确认正常；Steam 版也顺带确认绝大多数 DisplayFix 功能正常。

已经实机通过：

- 标题 / 主菜单保持原版 4:3；
- 进入游戏后切到目标宽屏；
- 游戏内 GUI / 主 HUD 正常居中；
- 右侧 6 个菜单按钮工作正常；
- Windows 高 DPI 环境下字体修复正常；
- 离开游戏并返回主菜单后，真实显示恢复为原版前端 4:3；
- Steam 环境下上述大部分功能也正常。

用户提供的 Steam 日志闭合了关键生命周期：

```text
[RUNTIME] Strategy enter state=3 GAMEPLAY profile=ready
[RUNTIME] Strategy enter original apply finished live=854x480 expected=854x480 force=1
...
[RUNTIME] Strategy exit old_state=3 FRONTEND profile=restored reset_mode=4 result=1 live=640x480 expected=640x480
```

### test1 唯一明确配置问题

当：

```ini
[Display]
Enable=0

[Font]
FixDPI=1
```

时，旧代码在读取完配置后立刻因为 `Display.Enable=0` 返回，导致字体补丁根本没有执行。这个问题不是字体签名失败，也不是宽屏逻辑问题，而是两个配置开关被错误耦合。

v0.1-test2 已把初始化顺序改成：

1. 读取 INI；
2. 先独立执行 `Font.FixDPI`；
3. 再判断 `Display.Enable`；
4. 如果 `Display.Enable=0`，只停止宽屏 / HUD / 输入等显示运行时补丁，字体修复结果保留；
5. 如果 `Display.Enable=1`，继续安装宽屏生命周期和 GUI / 输入 Hook。

因此 v0.1-test2 的配置语义正式固定为：

- `[Display] Enable` 只控制宽屏 / HUD / 输入主线；
- `[Font] FixDPI` 独立控制字体 DPI 修复；
- 两者互不依赖。

## 4. 已确认的外传关键地址

### 4.1 字体 DPI

- `GDI32!GetDeviceCaps` IAT：`0x00551054`
- 字体创建关键 CALL：`0x004C7760`
- 完整字体上下文文件偏移：`0x000C7759`
- `KERNEL32!MulDiv` IAT：`0x00551278`
- `CreateFontIndirectA` IAT：`0x00551050`

原代码通过 `GetDeviceCaps(..., LOGPIXELSY)` 读取系统实际 DPI，再把结果参与字体高度计算。修复采用本传已经实机通过、外传 test1 也已实机通过的等长 6 字节方案：

```text
原始：FF 15 54 10 55 00
修复：83 C4 08 6A 60 58
```

含义：手工清理原 stdcall 的两个参数，并模拟 `GetDeviceCaps` 返回 96 DPI。

### 4.2 显示模式函数与三处分辨率逻辑

- 原版显示模式函数：`0x0040BCC0`
- 模式派发签名：`0x0040BD0A`
- 第一处分辨率映射：`0x0047F09E`
- 第二处分辨率映射：`0x00489C1B`
- JMM 布局选择器：`0x004C69BB`

显示对象关键字段：

- `+0x04` 当前 mode ID
- `+0x08` 本轮准备 / 请求 mode
- `+0x228` live Width
- `+0x22C` live Height
- `+0x280` Strategy 使用的游戏设置 mode

显示模式函数存在“mode ID 相同且 force=0 时早退”的原版逻辑，因此只改同一 mode 的宽高立即数并不足以强制重建 Surface。

### 4.3 Strategy 生命周期

- Strategy 状态函数主体约：`0x0040B9C0`
- 旧 state=3 离开分支：`0x0040B9E8 -> 0x0040E0A0`
- 新 state=3 进入分支：`0x0040BA5F -> 0x0040E060`
- enter 内部显示模式 CALL：`0x0040E06F -> 0x0040BCC0`

`0x0040E060` 开头会以 `force=0` 调用显示模式函数。DisplayFix 在进入游戏这一小段调用期间临时把 `push 0` 改为 `push 1`，原函数返回后立刻恢复。test1 实机已经确认这样会得到真正的 `854x480` live Surface。

### 4.4 原版前端 mode 4

- 原版前端 mode 4 准备：`0x0040C339`
- 最终 CALL：`0x0040C345 -> 0x0040BCC0`

这证明外传标题 / 主菜单本来就有自己的原版 mode 4 生命周期。当前稳定设计不追求标题永久宽屏，而是：

1. 标题 / 开场 / 主菜单保持原版 4:3；
2. 进入 Strategy state 3 才切 GAMEPLAY 宽屏；
3. 离开 Strategy 后先原版清理，再恢复 FRONTEND profile；
4. 强制原版 mode 4 / force=1，真正重建回前端 4:3 Surface。

该完整循环已经由 test1 实机确认。

### 4.5 JMM / HUD / 输入

静态闭合地址：

- GUI/JMM 分辨率应用包装：`0x0040F9C0`
- JMM/UI 广播：`0x004C6970`
- JMM 资源路径构造：`0x00501DF0`
- 世界鼠标按下 callsite：`0x0040CFE6 -> 0x00482790`
- 全局鼠标释放 callsite：`0x0040CF80 -> 0x004C7930`
- 主 HUD 根类构造：`0x004D70A3`
- 主 HUD vtable：`0x00553B34`
- vtable+0x00：`0x004D7110`
- vtable+0x24：`0x004D8400`
- vtable+0x58：`0x004C5F00`
- ID 0x0B target global：`0x0058A2DC`
- ID 0x0E target global：`0x0058D3BC`
- active query：`0x004C5100`

用户 test1 已确认游戏内 GUI 居中和右侧 6 个按钮正常。Steam 日志也显示 0x0B / 0x0E 的 world-press 防穿透与 global-release 兜底路径正在工作。

## 5. 当前运行设计

### FRONTEND

启动后不永久宽屏化。前端代码保持该 EXE 自己的原始分辨率立即数与原始 JMM 选择，让开场、标题和主菜单走原版 4:3 生命周期。

### GAMEPLAY

当游戏自己的 Strategy state 3 进入时：

1. 把三个已确认显示模式分支映射到 `TargetWidth × BaseHeight`；
2. 同步两处分辨率映射；
3. 根据 BaseHeight 使用 JMMDL / JMMDL800 基线；
4. 临时把 Strategy-enter 内部 `force=0` 改为 `force=1`；
5. 让原版 `0x0040E060 -> 0x0040BCC0` 自己重建 Surface；
6. 原函数返回后恢复原始 force 字节；
7. 检查 live 宽高是否等于目标；只有验证通过才允许 HUD/JMM 宽屏逻辑继续。

### 回到前端

离开 Strategy 时：

1. 先执行原版 `0x0040E0A0`；
2. 清理游戏内 HUD 缓存；
3. 恢复 FRONTEND 原始立即数；
4. 把准备 mode 写回原版 mode 4；
5. 复用原版显示模式函数，以 `mode=4, force=1` 重建前端 Surface；
6. 核对 live 宽高是否恢复原版 mode 4。

## 6. 配置语义

推荐：

```ini
[Display]
Enable=1
BaseHeight=480
AspectRatio=Auto

[Font]
FixDPI=1

[GUI]
CenterMainHUD=1
```

### Display.Enable

`Enable=1`：启用宽屏 / HUD / 输入主线。

`Enable=0`：完全保留原版显示、HUD 与输入逻辑，但**不影响 `[Font] FixDPI`**。

### Font.FixDPI

`FixDPI=1`：独立应用 96 DPI 字体修复。

`FixDPI=0`：不修改字体 DPI 路径。

v0.1-test2 已修复 test1 的错误耦合，因此允许：

```ini
[Display]
Enable=0

[Font]
FixDPI=1
```

只修字体、不启用宽屏。

## 7. BaseHeight 结论

`BaseHeight` 是游戏内部逻辑高度，不是最终输出清晰度。

推荐稳定基线：

- 480 + 16:9 → 854×480
- 600 + 16:9 → 1068×600

更高值会真正扩大内部世界 Surface、可见范围与对象处理负担，可能严重降低帧数。4K 屏幕仍建议让游戏内部使用 480 / 600，再交给 cnc-ddraw 放大。

## 8. Steam 分支状态

Steam 当前仍不是正式主线，但 test1 顺带验证获得了新的事实：

- Steam 版 + cnc-ddraw D3D9 可运行；
- Steam 版上标题 4:3、进入宽屏、HUD 居中、高 DPI 字体和右侧 6 个按钮等大部分 DisplayFix 功能正常；
- 日志中 `ComeOn.dll` 会在成熟 HUD 阶段被检测，并触发继承自本传的 delayed JMM 路径；实机没有发现这一点破坏当前功能；
- cnc-ddraw OpenGL 后端仍会在开场动画结束后闪退。

因此当前策略是：不为了 test2 的配置修复扩大 Steam 运行时修改范围；保留现状，等非 Steam 主线稳定后再单独调查 OpenGL / DirectShow / DirectDraw 生命周期问题。
