# 《刀剑封魔录外传：上古传说》DisplayFix v0.1-test1 完整接档说明

## 1. 版本定位

这是外传非 Steam 版的第一轮完整适配测试包。目标不是直接宣布正式版，而是把本传 DisplayFix v0.3 已实机闭合的架构，逐项重新映射到外传 `ComeOn.exe`，并保持“按内容签名验证、不是按 SHA-256 锁版本”的原则。

本轮已经完成静态闭合并编译进插件的主线：

- 96 DPI 字体修复；
- fixed-Y / auto-X 动态宽屏；
- 标题/开场/主菜单保留外传原版 4:3 前端显示生命周期；
- Strategy state 3 进入游戏时切到目标逻辑分辨率；
- 同 mode ID 时临时 `force=1`，确保真实 DirectDraw Surface 真正重建；
- 离开 Strategy 后恢复 FRONTEND profile，再强制原版 mode 4 / force=1 回到前端 Surface；
- JMM 布局选择器按 480 系 / 600 系模板切换；
- 本传已通过的底部主 HUD 居中、0x0B/0x0E 顶部按钮和点击防穿透逻辑已在外传完成静态结构映射，但尚未做外传实机验收。

Steam 版专项逻辑在 v0.1-test1 中故意不启用。用户已经确认外传 Steam 版配 cnc-ddraw 时 D3D9 后端可运行，而 OpenGL 后端会在开场动画后闪退；该问题等非 Steam 版完成后单独调查。

## 3. 已确认的外传关键地址

### 3.1 字体 DPI

- `GDI32!GetDeviceCaps` IAT：`0x00551054`
- 字体创建关键 CALL：`0x004C7760`
- 完整字体上下文文件偏移：`0x000C7759`
- 后续 `KERNEL32!MulDiv` IAT：`0x00551278`
- 后续 `CreateFontIndirectA` IAT：`0x00551050`

原代码通过 `GetDeviceCaps(..., LOGPIXELSY)` 读取系统实际 DPI，再把结果参与字体高度计算。修复仍采用本传已经实机通过的等长 6 字节方案：跳过实际 DPI 查询、手工清理原 stdcall 参数、让 EAX 固定返回 96。

### 3.2 显示模式函数与三处分辨率逻辑

- 原版显示模式函数：`0x0040BCC0`
- 模式派发签名：`0x0040BD0A`
- 第一处分辨率映射：`0x0047F09E`
- 第二处分辨率映射：`0x00489C1B`
- JMM 布局选择器：`0x004C69BB`

显示模式函数和本传结构一致，内部仍使用：

- mode 6 / 隐藏分支；
- 800×600 分支；
- 640×480 分支。

历史宽屏 EXE 只修改隐藏/扩展分支以及两处分辨率映射，因此可以作为结构验证样本。

### 3.3 Strategy 生命周期

外传高层状态机与本传不是同一绝对地址，但语义保持一致。

已闭合：

- Strategy enter callsite：`0x0040BA5F`
- Strategy enter 目标：`0x0040E060`
- Strategy exit callsite：`0x0040B9E8`
- Strategy exit 目标：`0x0040E0A0`

`0x0040E060` 开头：

```asm
push esi
mov  esi,ecx
push 0
mov  eax,[esi+280h]
push eax
mov  [esi+08h],eax
call 0040BCC0
```

这和本传最终成功方案的关键语义完全一致：原游戏进入 Strategy 时本来就会重新应用当前 mode，但传入 `force=0`。如果 mode ID 没变，仅仅改写“这个 mode 对应的宽高”不会强制重建 Surface，因此插件在这一小段调用期间把 `push 0` 的立即数临时改成 1，原函数返回后马上恢复。

### 3.4 原版前端 mode 4

已确认启动前端存在：

- 原版前端 mode 4 应用：`0x0040C339`
- 最终 CALL：`0x0040C345 -> 0x0040BCC0`

也就是说外传和本传一样，标题/前端有明确的原版 mode 4 生命周期。v0.1-test1 因此不把标题永久宽屏化，而是：

1. 启动/标题保持原版；
2. 进入 Strategy 才启用目标宽高；
3. 退出 Strategy 后恢复原分支，并强制 mode 4 重建前端 Surface。

### 3.5 JMM / HUD / 输入

静态验证已确认：

- GUI/JMM 分辨率应用包装：`0x0040F9C0`
- JMM/UI 广播：`0x004C6970`
- JMM 资源路径构造：`0x00501DF0`
- 世界鼠标按下 callsite：`0x0040CFE6 -> 0x00482790`
- 全局鼠标释放 callsite：`0x0040CF80 -> 0x004C7930`
- 主 HUD 根类构造：`0x004D70A3`
- 主 HUD vtable：`0x00553B34`
- vtable+0x00：`0x004D7110`
- vtable+0x24：`0x004D8400`
- vtable+0x58：`0x004C5F00`
- ID 0x0B target global：`0x0058A2DC`
- ID 0x0E target global：`0x0058D3BC`
- 两分支 active query：`0x004C5100`

这些结构与本传高度同源，所以完整功能已经迁入 test1；但“结构相同”不等于“外传实机一定完全一致”，因此仍必须由用户验证。

## 4. 当前运行设计

### FRONTEND

启动后不立刻永久改写原版分辨率。前端代码配置保持原始 640/800/隐藏分支和原始 JMM 比较，让开场、标题和主菜单继续走游戏自己的 4:3 生命周期。

### GAMEPLAY

当游戏自己的 Strategy state 3 进入路径发生时：

1. 把三个已确认显示模式分支统一映射到 `TargetWidth × BaseHeight`；
2. 同步两处分辨率映射；
3. 按 BaseHeight 选择 JMMDL / JMMDL800 基线；
4. 临时把 Strategy-enter 内部的 `force=0` 改成 `force=1`；
5. 让原版 `0x0040E060 -> 0x0040BCC0` 自己完成真实 Surface 重建；
6. 原函数返回后恢复 `force=0`；
7. 核对 live 宽高是否真的等于目标。

### 回到前端

离开 Strategy 后：

1. 先执行原版 `0x0040E0A0` 清理；
2. 恢复所有 FRONTEND 原始立即数；
3. 把对象的准备 mode 写回 4；
4. 复用原版显示模式函数，调用 `mode=4, force=1`；
5. 核对 live 宽高是否回到该 EXE 自己保存的原始 mode 4 宽高。

## 5. 配置建议

第一轮实机建议：

```ini
[Display]
Enable=1
BaseHeight=480
AspectRatio=Auto

[Font]
FixDPI=1

[GUI]
CenterMainHUD=1
```

如果底部 HUD 出现位置或输入异常，可只把 `CenterMainHUD=0` 做 A/B；分辨率与字体主线仍可独立测试。

BaseHeight=480/600 是推荐基线。更高值会真正扩大内部世界 Surface 和可见范围，会增加老游戏的 CPU/GPU/DirectDraw 负载，不应把 1080 理解成单纯的“输出 1080p”。

## 7. Steam 分支状态

Steam 版目前不在 v0.1-test1 的验收范围内。

已知用户实机现象：

- cnc-ddraw D3D9 后端可以运行；
- cnc-ddraw OpenGL 后端会在开场动画结束后闪退。

Steam `ComeOn.exe` 会加载额外 `ComeOn.dll`，后续需要独立调查 DirectShow、窗口/DirectDraw 生命周期与 cnc-ddraw OpenGL 后端之间的冲突。本轮插件即使检测到 `ComeOn.dll`，也故意不启用本传继承来的 Steam delayed JMM 特殊路径。
