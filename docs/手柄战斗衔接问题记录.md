## 已核对的代码遗漏

1. 原版解析失败且历史已有结束标记时，会清除旧历史后由缓冲重试。本体 0x47546B..0x475473，外传 0x483CEB..0x483CF3；dev4 未实现该分支，导致无匹配的旧序列持续阻挡跨招式起手，直至历史整体超时。
2. 原版结束回调有准确的历史结束通知：本体 0x4699D0 调 0x475060，外传 0x477630 调 0x4838E0。仅在下一帧观察 ActiveRuntime 为空，会漏掉同一更新周期结束后立即续段的窗口。
3. dev4 有 pending 时拒绝新按键接管；而新按下 X/Y 是新的输入事件，不能被旧等待请求一直遮住。Y 仍按住时新按 X，也不能因 held 掩码仍含 Y 而继续当作右手。
4. dev4 把首次按下与重试都放在相同忙碌门后，并增加统一 100 ms 自动重复间隔。原版右手新按下入口会先尝试解析，而缓冲重试才检查 ActiveRuntime；原生动作是否接受由后续原版资格与 Dispatcher 决定。
5. 待处理输入的左右手信息与已提交动作共用字段，可能把较晚到达的执行通知归到新按键，错误推进预设游标。

## dev5 修正

- 接入两版原生结束通知，保留非手柄来源的原处理。
- 恢复“已结束历史不匹配→清历史→下一次重试”的规则。
- 新按键可替换旧等待请求，按新边沿决定左右手；两键同时保持时延续最后一次新边沿，不在下一帧固定切回 Y；首次尝试不被笼统 busy 门吞掉，但不手工取消 Runtime，原版仍决定是否能衔接。
- 初次尝试后最多五个后续更新周期重试，忙碌也消耗预算；资格暂时不满足时保留剩余次数，不无限积压。
- 去掉统一 100 ms 自动重复门。按住时仅在原版空闲且无待处理请求时再尝试。
- 分开 pending 与 issued 的来源，并用实际选择组匹配动作通知；不匹配的通知只记录，不推进手柄历史/右手预设。

## 验证边界

新增宿主回归使用首招时间条件为 0 的数据，覆盖 X→Y、Y→X、三项混合动作预设循环、同帧结束窗口及迟到通知归属。它比 dev4 的固定宽松条件更接近本次失败机制，但不是实际女侠资源表或真实游戏轨迹。两作均运行同样回归与静态检查，dev5 的实机衔接仍待用户确认。

移动算法、鼠标无关的目标/方向、投掷和模式切换必须继续回归，不能退回通过鼠标目标驱动技能的方案。
