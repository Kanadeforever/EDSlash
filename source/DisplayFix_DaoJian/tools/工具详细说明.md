# 工具详细说明

本目录只放 DisplayFix 主项目的三个 `verify_` 工具。

## verify_build.py

除 PE32/i386、DLL、入口点、InitializeASI、零 Import Directory 外，test8a 起还检查 `DisplayFix.ini` 的 UTF-8 可解析性、`[Display]` 前 BOM 保护行以及关键配置键是否存在。这样构建阶段就能阻止“第一节读不到导致 BaseHeight 静默回退 480”的发行回归。

用途：检查构建出的 `DisplayFix.asi`。

验证：

- PE32
- i386
- DLL 标志
- 非零入口点
- `InitializeASI` 导出名
- Import Directory 必须为 0
- 同目录 `DisplayFix.ini` 存在
- 输出 SHA-256

默认路径适配当前仓库结构，也可显式传入 ASI 路径。

## verify_compatibility.py

只读，不改 EXE。用机器码和结构关系判断一个 `ComeOn.exe` 是否兼容当前 DisplayFix。

当前验证包括：

- 字体 DPI 原始/已修复状态
- 分辨率派发与两处分辨率映射
- JMM 选择器
- `0x4087A0 -> 0x4B35F0`
- test10：`0x4B35F0 +0x1E -> 0x4EB9E0` 资源路径构造函数头，以及从 `BF imm32` 解析出的资源根目录缓冲区
- 主 HUD 构造/vtable/+0x24/+0x58
- 0x0B/0x0E 原版窗口开关结构
- 全局 release `0x406086 -> 0x4B4560`
- test8 世界 press `0x4060EB -> 0x473F10`

不再验证/安装 test7 的 0x4B44F0 wrapper，因为该方案已实机证明会破坏地图左键和 Alt+F4。

## verify_compatibility.bat

Windows 拖拽入口。把一个或多个 EXE 拖到 BAT 上即可批量调用 Python 兼容检查。

## 独立字体修复

独立永久字体补丁不在本 tools 目录，而固定放：

```text
source\FontFix_DaoJian\
```

它同样按目标机器码验证，不锁整体 SHA-256。

## v0.3-test8a 同步说明

- `v0.3-test8` 实机确认已经修复 test7 的普通地图左键 / Alt+F4 回归，并保留属性、道具两个顶部按钮响应；当前输入实现继续沿用 test8。
- test8 日志显示用户把 `BaseHeight` 改为 1080 后插件仍读取成 480。复核发行 INI 后确认 `[Display]` 原本正好位于 UTF-8 BOM 后的第一行；Win32 `GetPrivateProfile*A` 对 UTF-8 BOM 不可靠，第一节可能读不到，于是 `BaseHeight` 静默使用默认 480。test8a 将 INI 改为 UTF-8 无 BOM，并在 `[Display]` 前增加 ASCII 保护行，使以后编辑器即使重新加入 BOM，也不会再破坏第一节。
- test8a 日志新增 `ConfigPath=`，用于直接确认插件实际读取的是哪一份 `DisplayFix.ini`。
- `build.bat` 已按仓库位置重新整理：同时自动查找 PATH、`LLVM_HOME`、`LLVM_PATH`、`Program Files\LLVM` 和 Visual Studio 自带 LLVM，兼容本地与 Windows GitHub Actions；发行目录仍严格只有 ASI 与 INI。
- 主界面固定 640x480 的等比放大居中仍是后续任务，本轮没有处理。



## v0.3-test8b 构建同步说明

- test8a 的 `build.bat` 最后使用 `where /r` 递归扫描 Visual Studio，实机误选到 `VC\Tools\Llvm\ARM64\bin\clang.exe`，在 x64 Windows 上出现“映像文件无效 / 对另一种计算机类型有效”。该方案已判定失败。
- test8b 将编译器搜索精简为三层：PATH → `%ProgramFiles%\LLVM\bin` → `vswhere` 最新 Visual Studio 的 `VC\Tools\Llvm\x64\bin`；`clang.exe` 与 `lld-link.exe` 必须来自同一目录。
- 不再支持递归扫描、`LLVM_HOME`、`LLVM_PATH` 或任意 ARM64 LLVM 回退。找到工具后先运行 `--version`，无法在当前宿主执行时立即停止。
- `verify_build.py` 新增 build.bat 自检：禁止 `where /r`、禁止 ARM64 LLVM 路径、要求存在 x64 VS LLVM 回退，并检查 UTF-8 BOM + CRLF 以及所有有正文的 `REM` / `echo` 行末尾两个半角空格。
- test8b 后续实机日志已经确认 INI 第一节修复成立：Steam 与非 Steam 都能正确读取 `BaseHeight=720` 并计算 `1280x720`；这一项不再是阻塞。

## v0.3-test9 工具同步说明

- `verify_compatibility.py` 原本已经验证 `0x004087A0 -> 0x004B35F0` 包装关系；test9 的 Steam delayed UI sync 正是只读解析这套内容签名来取得 UI manager，因此原版与 Steam EXE 均已离线重新验证通过。
- test9 没有新增 EXE SHA-256 白名单，也没有新增 ComeOn.dll 版本白名单；Steam 运行条件是进程中实际存在 `ComeOn.dll`，代码地址兼容性仍由 ComeOn.exe 内容签名判断。
- `verify_build.py` 与 test8b 的精简 x64 LLVM/build.bat 约束保持不变。


## v0.3-test10 工具同步说明

- test9 实机证明“只广播顶层 `vtable+0x14`”无效后，test10 改为延迟调用完整原版 `0x4B35F0`。因此 `verify_compatibility.py` 新增了完整 JMM 前半段的结构证据检查。
- 新增验证：`0x4B35F0 +0x1E` 必须是 E8 CALL；目标函数头必须匹配 `56 57 BF <root-buffer> 83 C9 FF 33 C0`；解析出的资源根目录缓冲区必须落在 ComeOn.exe 已确认数据地址范围。
- 这项验证的目的不是锁死 `0x560168`，而是确保运行时用于 Steam 安全门槛的“资源根目录指针”确实来自原版资源路径构造代码。
- `verify_build.py`、build.bat 的 x64 LLVM 搜索/编码/REM/echo 约束继续保持 test8b 规则不变。
